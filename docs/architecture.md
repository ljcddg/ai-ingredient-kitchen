# AI 灵感厨房 · 技术文档

> **一句话**：用户挑食材 → 系统先在菜库里找现成的，命中高质量的直接返回；没有就让 AI 现场生成一道，
> 生成结果经校验后可发布进公共菜库，被搜索、被排名、被收藏。
>
> **阅读建议**：第 1–3 章是全局（给评审 / 面试讲解用）；第 4 章是核心链路（技术含量集中在这里）；
> 第 10–11 章是现状与拓展方向。

## 1. 业务闭环

```
                    ┌──────────── 用户选 / 输食材 ────────────┐
                    ▼                                        │
          ① 检索菜库（ES 粗排 + 应用层精排）                     │
                    │                                        │
        ┌─── 命中高质量（直出） ───┐         ┌── 未命中 / 质量不足 ──┐
        ▼                        ▼         ▼                     │
   直接返回结果              返回 + 说明原因  ② AI 生成（排队执行）    │
        │                                   │                    │
        │                           ③ 落库为草稿(0)              │
        │                                   │                    │
        │                           ④ 校验发布 → 已发布(1)        │
        │                                   │                    │
        └──────────── ⑤ 进索引 → 被检索 / 上榜 / 被收藏评分评论 ───┘
                            （内容沉淀回菜库，反哺 ① 的直出率）
```

闭环的关键在 ④ 和 ⑤：**没有"发布 + 进索引"这一步，AI 的产出一辈子搜不到，整个功能等于没闭环**。
所以「生成成功 → 自动试投一次发布」「撤回时同步删除索引」这两件事必须做。

## 2. 技术栈与版本矩阵

版本之间存在硬约束，改动前先看这张表：

| 组件 | 版本 | 约束说明 |
|---|---|---|
| JDK | 17 | 全局用 `jakarta.*`，不是 `javax.*` |
| Spring Boot | 3.2.4 | — |
| Spring Cloud | 2023.0.1 | 必须与 Boot 3.2.4 配对 |
| Spring Cloud Alibaba | **2023.0.1.0** | 三者必须严格对应；内含 Nacos Client 2.3.2 |
| MyBatis-Plus | 3.5.5 | 用 `mybatis-plus-spring-boot3-starter`（Boot 3 专用） |
| jjwt | 0.12.5 | 拆成 api / impl / jackson 三包 |
| Redisson | 3.26.1 | 内置 `redisson-spring-data-32`，匹配 Boot 3.2.x |
| MySQL 驱动 | 8.3.0 | 显式写 version，否则覆盖 Boot BOM 的管理 |
| Elasticsearch（服务端） | 8.16.0（Docker 容器 `es`） | 见下方说明 |
| Ollama | gemma4:e2b（5.1B，Q4_K_M） | 本地推理，一道菜 12~26 秒 |

### ⚠️ 为什么没用 Spring Data Elasticsearch

Spring Data ES 5.2.x（Boot 3.2.4 唯一能用的版本）官方兼容目标是 **ES 8.11.1**；现在的服务端是 **8.16.0**，比 8.11.1 更接近，但仍不是官方钉死的那个版本。
降回支持 7.x 的 4.4.x 又会破坏 Spring Framework 6.1 兼容 —— 跨不过 Boot 3 这条线。

**选择**：不引任何 ES 依赖，直接用 Spring 6.1 自带的 `RestClient` 发 JSON DSL。
它的价值是**零版本耦合** —— 同一份代码在 7.x 和 8.x 上都能跑：
服务端从 **7.16.2 换到 8.16.0，业务代码一行都没改**，这个判断事后被验证是有效的。
补充一个事实：ES 8 接受手写客户端发来的普通 `application/json`；只有官方 7.x Java 客户端才强制要求
`application/vnd.elasticsearch+json;compatible-with=7` 那种 vendor 头，所以这次切换不需要动代码。
代价是放弃 Repository 抽象 —— 而这里本来就要手写 DSL，实际没有损失。

## 3. 系统架构

### 3.1 模块划分

| 模块 | 端口 | 职责 | 关键内容 |
|---|---|---|---|
| `common-service` | — | 跨服务技术能力 | `Result<T>`、`BusinessException`、`JwtUtil`、`AuthConstants`、`JsonAutoConfiguration` |
| `account-service` | 8081 | 账号与认证 | 注册/登录、BCrypt、RBloomFilter、JWT 签发 |
| `dish-service` | 8082 | **业务核心** | AI 生成队列、检索、发布、互动、榜单、ES 同步 |
| `gateway` | 7000 | 统一入口 | JWT 鉴权过滤器、路由、CORS、限流预留 |
| `order-service` | — | 预留未放开 | 在父 pom 中处于注释状态 |

**依赖方向单向**：`account / dish / gateway → common`。
`common` 只放技术能力，**领域实体一律不进 common**（避免变成"什么都往里塞"的垃圾桶）。

### 3.2 两条铁律（自建父 pom 的代价）

项目用的是**自建父 pom**（没有继承 `spring-boot-starter-parent`），因此丢掉两样默认配置，必须显式补回：

| 补什么 | 不补的后果 |
|---|---|
| `spring-boot-maven-plugin` 手写 `<executions><goal>repackage</goal>` | 打出来的 jar **没有主清单属性**，根本起不来 |
| `maven-compiler-plugin` 开 `<parameters>true</parameters>` | `@RequestParam String q` 这类不写参数名的写法直接 500，且报错信息完全看不出根因 |

### 3.3 请求链路

```
浏览器 ──► :5500 前端（Vite / serve.py，代理 /api）
            │
            ▼
        :7000 gateway ── JwtAuthGlobalFilter（order = -100）
            │              ① 剥掉路由前缀 ② 查白名单
            │              ③ 删掉外部伪造的 X-User-Id ④ 验签 → 写回可信 X-User-Id
            ├── /api/account/** ──► account-service :8081
            └── /api/dish/**    ──► dish-service    :8082
```

网关鉴权有两个容易踩的点：

- **白名单写的是「剥掉前缀之后」的路径**：前端请求 `/api/account/auth/login`，网关 `StripPrefix=2` 后
  下游收到 `/auth/login`，所以白名单里要写 `/auth/**`。**新增路由必须同步维护前缀清单**。
- **必须先删除外部传入的 `X-User-Id` / `X-Username`**，再写入校验后的值。
  否则任何人手动带一个 `X-User-Id` 头就能越权 —— 这是网关鉴权最典型的漏洞。

### 3.4 配置治理（三层分工）

| 层 | 放什么 | 为什么 |
|---|---|---|
| 本地 `application.yml` | `spring.application.name`、`nacos.server-addr`、`spring.config.import`、`jwt.secret` | 启动前就得知道（找配置中心本身要用），密钥不入配置中心 |
| Nacos `common.yaml` | datasource、mybatis-plus、`spring.data.redis` | 多服务共享 |
| Nacos `<服务名>.yaml` | `server.port`、`jwt.expire-millis`、`bloom.*`、`es.*` | 服务专属 |

**关键规则**：`spring.config.import` 的**导入顺序就是优先级**（后导入的覆盖先导入的），
所以 `common.yaml` 必须放在第一个。项目内 `nacos-config/` 是留档副本，需与 Nacos 保持一致。

## 4. 核心链路

### 4.1 认证链路

**注册（布隆过滤器前置拦截）**

```
用户名 → mightContain?
   ├─ false（100% 准）→ 直接拒绝「用户名已存在」，不查库
   └─ true（可能误判）→ 查库确认 → 不存在才走 BCrypt → 落库 → 布隆 add
```

**布隆过滤器的铁律**（这套是 Redisson `RBloomFilter`，100 万容量 / 误判率 0.01）：

1. 说「**不存在**」100% 可信 → 直接拒；
2. 说「**存在**」可能是误判 → **必须查库确认**，不能直接拒。
   把这两条搞反，会把正常用户挡在门外（假阳性）或放进重复用户名（假阴性）。
3. 注册成功后**必须 `add`**，否则下一次注册的拦截失效。

**Redis 不可用必须降级，绝不能让服务挂**：

| 场景 | 处理 |
|---|---|
| 初始化 | Redisson 开 `lazyInitialization`，不在启动期强连 |
| `mightContain` 失败 | 一律返回 `true`（即"继续走查库"，宁可慢不可错） |
| `add` 失败 | 只记 `pendingWrites`，**绝不抛异常** —— 注册方法带 `@Transactional`，抛出去会把用户已经写好的账号回滚掉 |
| 连续失败 | 进入 30 秒冷静期（`degradeUntil`），期间直接走降级路径 |
| 预热 | 用 `count()` 与库内记录数比对，**偏少就全量补齐**（Redis 重启后布隆会退化成"基本全 false"） |

**登录与鉴权**：登录校验 BCrypt → 签发 JWT（有效期 2 小时）→ 之后所有请求由网关验签，
并把 `userId / username` 以请求头形式传给下游服务。**gateway 与 account-service 的 `jwt.secret` 必须完全一致**，
差一个字符就是全线 401。

### 4.2 AI 做菜链路

**为什么必须异步**：本地 5.1B 模型生成一道菜要 **12~26 秒**，用户不可能对着转圈等。
所以 `POST /ai/dish` 立即返回 `taskId`，前端轮询 `GET /ai/tasks` 拿进度。

**为什么自建队列而不是用现成的**：

| 方案 | 为什么不合适 |
|---|---|
| `ThreadPoolExecutor` + 阻塞队列 | 任务入队后**无法调整顺序**，拿不到稳定的"我排第几" |
| `PriorityBlockingQueue` | 只在插入时排序，插入后**无法重排** —— 与"用户改顺序"直接冲突 |
| MQ（RocketMQ / RabbitMQ） | 「用户改顺序」「取消排队」在 MQ 模型里非常别扭，还要额外维护一份位置状态，多一个组件换不到收益 |

**自建 `DishTaskQueue`**：一个 `lock` 保护的有序 `List` 做等待队列（重排需要整体可见的顺序，
无锁队列反而更难写对；队列操作频率极低，锁竞争可忽略）+ `ConcurrentHashMap` 记录执行中任务。

```java
// 调度线程骨架
while (!interrupted) {
    synchronized (lock) {
        while (waiting.isEmpty() || running.size() >= concurrency) lock.wait();
        next = waiting.remove(0);
        running.put(next.taskId(), next);
    }
    executor.submit(() -> runAndFinish(next));   // ← 交给执行线程池，调度线程绝不自己执行
}
```

> **调度线程绝不能自己执行任务**：否则它跑一个 10 秒的生成时，没人接新任务，
> 用户提交后连"排队中"的状态都拿不到。

**任务状态机**：`PENDING → RUNNING → SUCCESS / FAILED`，任意阶段可 `CANCELLED`。
`SUCCESS / FAILED / CANCELLED` 都是**终态**，且**只有 PENDING 和 RUNNING 可被取消**。

**关于"取消执行中的任务"要如实说明**：`Future.cancel(true)` 只是打中断标志，
Ollama 的 HTTP 调用是阻塞 IO，**中断不一定能让请求真的停下来**。所以：

- 排队中取消 = **真省资源**（根本没开始）
- 执行中取消 = **逻辑取消**（不入库、前端立即看到取消），服务端资源可能仍被占用一小会儿

要做到真正省资源，需要改用流式调用（`stream=true`）+ 回调里检查中断标志。
这是一个明确的优化项，当前版本**有意不做**。

**并发与配额**：`ai.queue.concurrency` 默认 **1**（本地单模型串行最稳，实测热态 3~4 秒/次）；
`ai.queue.max-per-user` 默认 **5**，防止连点把队列排到天荒地老。

**输出质量控制：三道防线**（只靠提示词是不够的，小模型长输出会漂移）

| 防线 | 做法 | 作用 |
|---|---|---|
| ① 系统提示词 | 明确 JSON 结构 + 字段规则 + 用量范围 | 告诉它要什么 |
| ② `format: "json"` | Ollama 的约束解码参数 | 实测有效：不加会裹 ` ```json ` 代码块 |
| ③ 应用层校验 + 重试 | 逐字段校验类型/范围，不合格把**具体原因**拼回提示词重试 **1 次** | 兜住小概率 |

> 失败信息要分两份：给用户的是人话（「AI 没能用「X」想出合适的做法，换个搭配再试试」），
> 给模型的是字段级细节（「prepTimeMin=0 不在 2~60 之间」）。把后者直接展示给用户等于没说。

**实测发现过的两个真实问题**（都已修）：

- AI 会给出「料酒 300g」这种离谱用量，直接污染营养计算 → 提示词补了用量范围 + 应用层钳制
- 加了用量限制后，小模型**干脆不列调料了**（盐、油、酱油全消失），导致炒菜漏掉约 135 千卡油热量
  → 采用 **Plan A**：`ingredients` 只放主料/辅料（参与营养计算），调料另设 `seasonings` 字段，
  **AI 只答"要哪几样"，用量由系统按标准配方补**。职责清晰：AI 给"有什么"，系统给"多少"。

**服务重启处理**：内存队列一重启就没了，但库里还留着 `PENDING / RUNNING` 的记录，
不处理就永远卡在"生成中"。启动时用 `ApplicationRunner` 把它们标记为 `INTERRUPTED`。
**有意不做自动重新入队** —— 任务可能已经写了一部分草稿，重放会产生重复数据，让用户自己决定要不要重试更安全。

### 4.3 发布与索引同步

- **发布 = 草稿(0) → 已发布(1) + 写 `publish_time`**。
- 两条路径**共用同一套校验**：生成成功后自动试投一次 + 手动 `POST /ai/dish/{id}/publish`。
- 发布门槛：**食材数 ≥ 2**（数的是"能被搜到的食材总数"，不是"主料 ≥ 2" ——
  落库只把 AI 输出的第一个食材标成主料，按主料数会把「土豆 + 胡萝卜」也拦下来）。
- **索引里只放已发布的菜**；撤回 / 下架必须把索引那份删掉，否则出现「搜得到但点进去说不存在」。

**同步机制靠领域事件**：

```java
@TransactionalEventListener(phase = AFTER_COMMIT)   // 事务提交后才写 ES
```

> 两个必须注意的点：① **发布方法必须带 `@Transactional`**，否则监听器静默不执行；
> ② 不要在事务体里直接写 ES（ES 失败不会回滚 MySQL，且可能读到未提交的旧数据）。

**三条同步路径**：启动时 `ensureIndex` 自愈 → 发布后增量 → 每天 04:00 全量重建（`es.reindex.cron`）。

### 4.4 检索链路

**分工**：ES 只做粗排（回答"含不含这些食材"），**覆盖率计算与应用层精排、直出判定都在应用层**。

**核心查询设计**：`terms` 查询**默认是 OR 不是 AND** —— 这是 90% 的人第一次用 ES 做"包含全部"时踩的坑。
要表达"必须全部包含"，只能**每种食材拼一个独立 `term` 放进 `must` 数组**，
并且这个拼装**只允许在一处**（`EsDslBuilder.buildIngredientClause`）做，避免各写各的。

**两条召回路**（这是让"表外食材"也能被搜到的关键）：

| 食材类型 | 查询字段 | 说明 |
|---|---|---|
| 有主数据 ID 的（如「番茄」→ id=101） | `ingredientIds`（long 数组） | 精确匹配 |
| 表外食材（用户自由输入的，如「松露」） | `ingredientNames`（keyword 数组） | 没有这条路，用了它的菜**谁也搜不到** |

**为什么逐项 `term` 而不是用 `terms` 数组**：`terms` 一次只能查一个字段，而这里要混合两种字段；
逐项之后"命中几个子句"就等于"覆盖几样食材"，**覆盖率可以直接数出来**。

**直出规则**（确定性规则，同输入同输出）：

```
覆盖率 ≥ 0.8  且  评价人数 ≥ 10  且  威尔逊分 ≥ 0.84
```

不满足时也**不返回空**，而是带上**可解释的 missReason**（「最接近的『番茄土豆汤』评分偏低（0.70 < 0.84）」），
前端据此提示"要不要让 AI 生成一道"。

**降级**：ES 不可用时**返回空列表而不是抛异常**，前端自然走到"AI 生成"分支 —— 检索挂了不影响主流程。

### 4.5 互动与榜单

| 能力 | 关键设计 |
|---|---|
| **收藏** | **恢复式**：取消走逻辑删除，再收藏用 `ON DUPLICATE KEY UPDATE deleted = 0`；**计数按明细表重算**，绝不用 affected rows 做加减 |
| **评分** | 一人一票靠唯一索引 `uk_dish_user`；打分后重算 `rating_avg / count / wilson` |
| **排行榜** | `GET /ai/rank?type=hot\|top\|latest`，**只统计已发布的菜**。热门 = 收藏×3 + 评分×2；高分按**威尔逊下界**（不是平均分）；最新按 `publish_time` |
| **评论** | 与评分**分两张表**：评分是"一人一票的数值"，评论是"可多条的文字"，语义不同 |

**为什么用威尔逊下界而不是平均分**：一道菜 1 个人打 5 分（平均 5.0）不该压过
100 个人打 4.6 分的菜。威尔逊区间下界会对样本量小的评分做惩罚，**天然抗刷分**。
SQL 侧与 ES 侧的威尔逊口径必须一致（p = 平均分/5，z = 1.96），否则两边排序会对不上。

**草稿可见性**：`status=0` 的菜**只有创建者可见**，详情 / 收藏 / 评分 / 评论四处都要校验，
提示统一为「菜品不存在」（不暴露"存在但你没权限"）。

### 4.6 食材沉淀：候选 → 转正

用户自由输入的食材（「松露」「姬松茸」…）如果直接写进主数据，会让垃圾输入（甚至「狗屎」）污染基准。
所以走一条沉淀路径：

```
自由输入食材 → 记录用量到 t_ingredient_candidate
        → 累计出现 ≥ 3 次（PROMOTE_THRESHOLD）
        → 转正：写 t_ingredient + 回填历史明细 ID + 标记候选已转正 + 重写受影响菜的索引
```

两个容易忽略的点：

- **记录动作跑在落库事务里，绝不能抛异常** —— 抛出去会把用户等了 20 秒的菜直接回滚掉。
- **转正后必须重写索引**，否则"转正了但搜不到"，等于白转。
- 转正食材的 `calorie = 0` 表示「还不知道」，营养校验时要把 `calorie <= 0` 当作**没数据放弃**，
  否则会把整道菜的热量压低，触发"偏差过大"误报。

## 5. 数据模型

**账户库**

| 表 | 用途 |
|---|---|
| `t_user` | 用户（用户名唯一、BCrypt 密码、逻辑删除） |

**菜品库（11 张）**

| 表 | 用途 | 关键约束 |
|---|---|---|
| `t_ingredient` | 食材主数据（88 条，含每 100g 营养） | 归一化与营养计算的**基准** |
| `t_ingredient_candidate` | 表外食材用量沉淀 | 累计 3 次转正 |
| `t_dish` | 菜品主表 | `status`(0 草稿/1 已发布)、`deleted`、`publish_time`、`rating_avg/count/wilson`、`collect_count` |
| `t_dish_ingredient` | 菜品-食材明细 | 含用量与是否主料 |
| `t_dish_step` | 制作步骤 | `(dish_id, step_no)` |
| `t_dish_rating` | 评分 | 唯一索引 `uk_dish_user` 保证一人一票 |
| `t_dish_comment` | 评论 | 与评分分表 |
| `t_dish_collect` | 收藏 | 逻辑删除 + `ON DUPLICATE KEY UPDATE` 恢复 |
| `t_ai_generate_task` | AI 生成任务 | 状态机、`error_msg`、`finish_time` |
| `t_tag` / `t_dish_tag` | 标签 | 口味标签参与检索权重 |
| `t_user_ingredient_pref` | 用户食材偏好 | **已建表，尚未用起来**（见第 11 章） |

**几个通用约定**：主键统一 `IdType.ASSIGN_ID`（雪花）、`@TableLogic` 逻辑删除、
时间字段 `@TableField(fill)` + `MetaObjectHandler` 自动填充。

> **雪花 ID 必须序列化成字符串**：19 位数字超出 JS `Number` 的精度范围，
> 直接返回前端会精度丢失、详情页 404。项目在 common 里用 `JsonAutoConfiguration`
> 把**所有 `Long` 统一序列化为字符串**，零配置生效。前端因此**一律把 ID 当字符串**，禁止 `Number(id)`。

## 7. 关键设计决策与取舍

| # | 决策点 | 选择 | 放弃了什么 | 理由 |
|---|---|---|---|---|
| 1 | ES 客户端 | 手写 `RestClient` | Spring Data 的 Repository 抽象 | Spring Data ES 5.2.x 的目标是 ES 8.11.1，服务端 8.16.0 仍不是官方钉死的版本；手写 RestClient 零版本耦合（7.16.2 → 8.16.0 业务代码一行未改）；DSL 本来就要手写 |
| 2 | 生成调度 | 自建内存队列 | MQ 的可靠性 / 天然分布式 | MQ 表达不了"改顺序 / 取消排队"；单实例下自建更简单可控 |
| 3 | 并发度 | 默认 1 | 吞吐 | 本地单模型串行最稳，且实测不慢 |
| 4 | 营养来源 | AI 估算 + 标注「仅供参考」 | 本地精确计算 | 食材可自由输入，主数据不可能全覆盖；本地计算降级为后台校验 |
| 5 | 调料用量 | Plan A：AI 只答"要哪几样" | AI 全权给用量 | 小模型给用量会幻觉（料酒 300g）；油热量漏掉会让整道菜热量差近一倍 |
| 6 | 表外食材 | 候选表沉淀 + 3 次转正 | 直接进主数据 | 主数据是计算基准，垃圾输入会污染整个召回链路 |
| 7 | 排序口径 | 威尔逊下界 | 平均分 | 平均分挡不住"1 人打 5 分"压过"100 人打 4.6 分" |
| 8 | 执行中取消 | 只做逻辑取消 | 立刻释放资源 | 需要流式 + 断连改造，收益不抵复杂度（明确记为优化项） |
| 9 | 重启恢复 | 标记 INTERRUPTED | 自动重新入队 | 重放会产生重复草稿，让用户自己决定更安全 |
| 10 | ID 传输 | 全部 `Long` → String | 少一次转换 | 雪花 ID 19 位超 JS 精度，不转就丢精度 |

## 8. 非功能性设计

**降级矩阵**（每个外部依赖挂掉时的行为）

| 依赖 | 挂掉后的表现 | 设计意图 |
|---|---|---|
| Redis | 注册/登录仍可用（布隆降级为"直接查库"） | 缓存不可用不能等于服务不可用 |
| Elasticsearch | 检索返回空列表 → 前端引导走 AI 生成 | 检索是加速器，不是主流程的必要条件 |
| Ollama | 生成任务标记失败，提示用户重试 | 失败要说人话，不无限重试烧资源 |
| MySQL | 无降级（唯一强依赖） | source of truth |

**安全**：密码 BCrypt 明文不落库不返回；网关强制校验并**清除伪造的身份头**；
草稿内容严格隔离；所有查询都带 `status` + `deleted` 过滤，杜绝草稿泄漏与已删除数据回流。

**可观测性**：关键链路（生成耗时、校验失败原因、ES 降级、布隆降级）均有明确日志级别，
字段级错误只进日志不进用户提示。

**性能要点**：生成类请求全部异步；检索走 ES + 应用层精排；计数类字段（收藏 / 评分）预聚合在 `t_dish` 上，
避免列表页 N+1；ES 写入用业务主键做 `_id`，天然幂等。

## 9. 本地运行

**启动顺序**：MySQL / Redis / Nacos / Elasticsearch / Ollama → gateway → account → dish → 前端。

**⚠️ 本机启动两条铁律**

1. **必须显式传 `--server.port`**：运行环境会注入 `SERVER__PORT` 环境变量，
   Spring Boot 的宽松绑定会把它当成 `server.port` 且优先级高于配置文件，
   服务于是去抢宿主任意端口（报 `Port 53482 was already in use`，且这个端口号每次都不同）。
   命令行参数优先级最高，写死即解决。建议同时 `unset SERVER__PORT SERVER__HOST`。
2. **命令行必须加 `-Dfile.encoding=UTF-8`**：JDK 17 在 Windows 中文环境下默认编码仍是 GBK
   （默认改 UTF-8 是 JDK 18 的 JEP 400）。Nacos 上的配置带中文注释，
   用 GBK 去解 UTF-8 字节会失败；而这个异常被 `optional:` 前缀吞掉，只留一行 ERROR，
   最终暴露出来的是 `Failed to determine a suitable driver class` —— 看起来完全是数据源问题。
   （IDEA 启动默认带这个参数，所以 IDEA 里不会遇到。）

**打包注意**：`package` 前先 `clean`，且**先停掉正在运行的服务**；
单独打业务模块要带 `-am`，否则 fat jar 会嵌进本地仓库里的旧 `common-service`，
症状是 `Long` 不再序列化成字符串、前端雪花 ID 精度丢失、详情页 404。

## 11. 业务拓展方向

按**投入产出比**分三档。判断依据：能否复用已有表和接口、是否补齐当前明显缺口。

### A 档｜低成本延伸（复用现有能力，适合先做）

| # | 方向 | 为什么现在能做 | 要动的地方 |
|---|---|---|---|
| 1 | **AI 菜品配图** | 菜谱无图，视觉体验是当前最明显的短板；生成链路已异步，加一步不阻塞 | 生成成功后追加出图任务 → `t_dish.cover_url`，卡片与详情页展示 |
| 2 | **一键买菜清单** | `t_dish_ingredient` 里已有食材 + 用量，导出即用 | 新增 `/ai/dish/{id}/shopping-list`，按品类分组；后续可对接生鲜平台的商品 ID |
| 3 | **食材候选运营后台** | `t_ingredient_candidate` **已经在攒数据了**，不做就白攒 | 一个审核列表页 + 转正按钮（转正接口已存在） |
| 4 | **菜名搜索** | `name` 字段已是 text + keyword 双字段，为搜索预留好了 | 装 ik 分词器（注意按 ES 版本号下同版本），加 `/search` 的菜名分支 |
| 5 | **菜谱分享长图** | 详情页数据齐全，纯前端渲染导出 | 步骤 + 营养 + 二维码（带回流参数），零成本社交裂变 |

### B 档｜中等投入（需要新表或新链路）

| # | 方向 | 价值 | 关键点 |
|---|---|---|---|
| 6 | **营养目标反向生成** | 从"给我食材我做什么"变成"我要减脂，给我一周菜谱" —— **从工具变服务的关键一跳** | 新增用户健康档案（目标 / 忌口 / 过敏原）；生成时把目标写进提示词；输出一周计划 + 自动购物清单 |
| 7 | **个性化推荐** | 解决"选择困难"，提升直出率 | `t_user_ingredient_pref` 表**已建但未用**；先做规则（常选食材加权），再上协同过滤 |
| 8 | **对话式厨艺助手（RAG）** | 做饭时手不干净，语音问答比翻页面自然得多 | 把菜库 + 步骤向量化，做"为什么我的番茄炒蛋出水"这类问答；与队列共用 Ollama |
| 9 | **会员 / 排队权益** | 本地单模型是天然瓶颈，**瓶颈本身就是商业化入口** | 令牌桶限流 + 优先队列（会员插队、每日生成额度）；队列已支持重排，加优先级成本低 |
| 10 | **社交关系链** | 已有发布 / 评论 / 评分，缺的只是"人"的连接 | 关注、大厨榜、"今天有 128 人做了这道菜"、每周做法挑战赛 |

### C 档｜长期 / 商业化

| # | 方向 | 说明 |
|---|---|---|
| 11 | **拍照识别食材** | 冰箱剩菜拍照 → 能做什么菜。解决"我不知道该搜什么"，直连现有检索链路 |
| 12 | **B 端标准配方** | 给餐饮小店做菜单生成 + 标准化配方卡（含成本核算），是清晰的付费场景 |
| 13 | **多实例化改造** | 队列迁 Redis ZSet、服务无状态化。这是"能扛量"的前置条件，也是第 9 项的商业前提 |
| 14 | **内容生态** | 开放 UGC 菜谱投稿（当前只有 AI 生成路径），配合审核后台形成内容池 |

### 如果只选三件

1. **AI 配图**（体验提升最直观，投入最小）
2. **食材候选运营后台**（数据已经在攒，做完立刻让菜库自我扩张）
3. **营养目标反向生成**（唯一一个能把产品从"生成器"变成"饮食服务"的方向）

> 前两项是"补齐短板"，第三项是"打开天花板"。第 9 项（会员/排队权益）建议在用户量起来后再做，
> 现在做会因为体验本身还不够好而流失用户。
