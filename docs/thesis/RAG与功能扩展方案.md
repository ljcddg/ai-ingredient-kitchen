## 二、你现在离 RAG 有多远

现状（`ReferenceDishRetriever` + `ai.generate.mode`）：

```
用户约束 ──► 取食材 ID 集合 ──► ES term 检索相似菜谱 ──► 整段拼进提示词 ──► Ollama 生成 ──► 三道防线校验
                                        ↑
                                  只有"检索→拼接"这一跳
```

这已经是 **RAG 的雏形**（Lewis 的 RAG-Sequence 简化版），缺的是四件事：

| 缺口 | 表现 | 论文里的对应 |
|---|---|---|
| 检索只有字面匹配 | 食材是 keyword+term 精确匹配，同义/近义（西红柿/番茄要看别名表）覆盖不到语义相似 | 混合检索（Brown 综述的共识） |
| 上下文无结构 | 参考菜谱整段文本塞进去，噪声大、token 浪费 | 结构化上下文包装 |
| 没有"依据"概念 | 生成出来的用量对不对，只能靠规则上限兜 | faithfulness / grounding 校验 |
| 没有归因闭环 | 校验失败只说"失败了"，不知道是检索没给到还是模型编的 | 失败分档归因 |

## 三、RAG 目标架构：四段式

```
① 离线索引            ② 在线检索              ③ 受约束生成           ④ 归因与评测
┌─────────────┐      ┌──────────────┐       ┌──────────────┐      ┌─────────────┐
│ 菜谱卡构建   │      │ 结构化 query  │       │ 上下文模板    │      │ 依据校验     │
│ 食材卡构建   │ ───► │ 混合召回      │ ───►  │ format=json  │ ───► │ 失败分档     │
│ 向量化+入索引│      │ 重排(top-k)   │       │ 低温生成      │      │ 三指标评测   │
└─────────────┘      └──────────────┘       └──────────────┘      └─────────────┘
     EsSyncWorker 扩展      新增 Retriever        改造 PromptBuilder      新增 Attribution
```

### 3.1 ① 离线索引：索引单元是"菜谱卡"，不是整篇菜谱

Brown 综述里 128 篇的分块策略五花八门（600 字符定长、按句、按行）。**你的场景不该做滑动窗口分块**——菜谱是结构化数据，天然的分块边界就是"一道菜"。按整卡入索引有三个好处：不会把配料表和步骤切断、检索命中即可直接用、token 可控。

菜谱卡字段设计（新增 ES 索引 `dish_card_v1`，或给现有索引加字段）：

| 字段 | 类型 | 用途 |
|---|---|---|
| `dish_id` / `name` | keyword / text | 标识与名称召回 |
| `main_ingredient_ids` | keyword[] | 满足率计算、must 全含 |
| `main_ingredient_names` | keyword[] | 表外名称兜底 |
| `ingredient_category_ids` | keyword[] | 缺料上限过滤、替代推荐 |
| `cook_time` / `difficulty` / `servings` | integer / keyword | 硬过滤 |
| `steps_brief` | text | 上下文正文（截断到 200 字） |
| `nutrition` | object | 营养区间，供 grounding 校验 |
| `rank_level` / `wilson_score` | integer / double | 质量分与排序 |
| `card_vector` | dense_vector | 向量召回（见 3.2 方案 B） |

写入链路复用现有机制：`@TransactionalEventListener(AFTER_COMMIT)` → `EsSyncWorker`（5/15/45/120s 退避），只需在同步时**多算一个 vector 字段**，不需要新组件、不需要新事务边界。这是最省事的一步。

### 3.2 ② 在线检索：三档决策 + 混合召回

**决策档位**（把现有的 `directReturn` 布尔升级为三态，这一条是给论文"机会成本"问题用的）：

| 档位 | 触发条件 | 动作 | 期望收益 |
|---|---|---|---|
| `DIRECT` | 满足率 ≥ 0.8 且质量分达标 | 直接返回，**不调用模型** | 省掉 12~26s |
| `RAG_GENERATE` | 满足率 0.4~0.8，检索到 ≥1 张可用卡 | 检索 + 生成 | 有参考，幻觉少 |
| `GENERATE_FRESH` | 满足率 < 0.4 或无可用卡 | 无参考生成（现有链路） | 保底可用 |

每次决策把 `(query_hash, 档位, 命中数, 满足率, 耗时, 是否回退)` 写进 `t_retrieval_decision`。这张表就是你论文里"检索优先到底省了多少调用"的**唯一证据来源**，没有它第 5 章写不出数。

**混合召回，两档实现，按你的时间选**：

- 方案 B（零新依赖，先做这个）：现有的 `term` 精确匹配 + `more_like_this`（食材字段相似）+ 字段加权（`main_ingredient_ids^3`、`ingredient_category_ids^1`）。全部在现有 ES 里，不改部署。
- 方案 A（加向量，做对照实验用）：`card_vector` 用 Ollama 的 `bge-m3` 生成（走你已有的 Ollama，不装新 Python 包）。ES 侧用 `dense_vector` + `knn` 查询，与 lexical 结果做 RRF 融合（`score = Σ 1/(60+rank)`）。

> 版本提醒：`dense_vector` 从 ES 7.3 起可用，`knn` 顶层查询从 8.0 起。开做前先 `GET /` 确认版本，7.x 需要用 `script_score` 写法，差别不小。

**重排**：召回 top 20 后按 `0.5×满足率 + 0.3×质量分 + 0.2×时长匹配` 重排，取前 3 张入上下文。排序公式与现有 `0.45/0.30/0.15/0.10` 保持同一套口径，别在论文里出现两套权重。

### 3.3 ③ 受约束生成：上下文模板化 + 低温

Brown 综述里有一句对你特别有用：*"explicit prompt policies（明确 grounding clause、zero-temperature reasoning、领域 wrapper）常能匹敌甚至超过换一个新检索器"*。也就是说，**prompt 策略比换检索器性价比高**。

上下文模板（固定五段，只填字段，禁止塞自由文本）：

```
【可用食材】胡萝卜(ID:12)、土豆(ID:31) …（来自归一化结果，禁止改写）
【硬约束】必用：胡萝卜；禁用：辣椒；人数：2；上限时长：30 分钟
【参考菜谱-1】宫保鸡丁｜主料：鸡胸/花生/黄瓜｜用时 25min｜难度 2｜用量：鸡胸 250g/2人
【参考菜谱-2】…
【输出要求】只输出 JSON；配料表每一项必须来自【可用食材】或【参考菜谱】；
             用量若与参考菜谱不同，须在 notes 里说明理由
```

三个细节：
1. **只给结构化字段，不给步骤全文** → 噪声少、token 省、模型不容易抄跑偏。
2. **`temperature=0.2`**，`format=json` 保留。你现在的 12~26s 里有一部分是重试消耗，低温能直接降重试率。
3. **参考卡数量 3 张**，不是越多越好。小模型（gemma4:e2b）上下文有限，3 张卡 ≈ 600 token，留足输出空间。

### 3.4 ④ 归因与评测：这是最能出论文成果的一块

**依据校验（grounding check）—— 建议作为你的一个创新点**

思路很朴素：生成结果里每一个"用量"，都应该能在【参考菜谱】或【可用食材】里找到出处。找不到出处 = 模型自己编的。

```
对生成结果的每个 (食材, 用量, 单位):
  ├─ 在参考卡里找到同食材同量级  → GROUNDED（有依据）
  ├─ 在参考卡里找到同食材但量差 >2 倍 → DEVIATED（有依据但偏离，记入归因）
  └─ 参考卡里没有这个食材        → UNGROUNDED（幻觉嫌疑）
```

这条规则的好处：**全自动、可复现、不需要人工标注**，正好补上 Brown 综述点出的"检索噪声 vs 生成流畅度缺系统评测"这个 gap。第 5 章可以直接报三个比例。

**三指标口径**（对齐 ARES / RAGAS，写进论文评价标准那一节）：

| 指标 | 本项目怎么算 | 数据来源 |
|---|---|---|
| Context Relevance | 召回的 top-3 卡中，主料与用户食材集合的交集 / 并集 | `t_retrieval_decision` |
| Answer Faithfulness | `GROUNDED / (GROUNDED+DEVIATED+UNGROUNDED)` | `t_generation_attribution` |
| Answer Relevance | 生成结果的主料覆盖用户必用食材的比例 | 同上 |

**失败分档**（现有"校验失败"太粗）：

| 分档 | 判据 | 处置 |
|---|---|---|
| `RETRIEVAL_MISS` | 参考卡为空或交集为 0 | 不该重试，直接降 `GENERATE_FRESH` |
| `FORMAT_FAIL` | JSON 解析失败 | 重试 1 次（现有逻辑） |
| `CONSTRAINT_FAIL` | 必用/禁用/用量违反 | 把违反项**具体回注**提示词再试 1 次 |
| `GROUNDING_FAIL` | UNGROUNDED 比例 > 0.3 | 记录但不重试，标注"低可信" |

现有代码是"重试耗尽直接 FAILED"，加上分档之后 `RETRIEVAL_MISS` 不浪费一次重试，`CONSTRAINT_FAIL` 的重试命中率也会明显提高（因为回注的是具体项而不是"再试一次"）。

## 五、分阶段实施

**P0（先做，2~3 天，纯增量不改老链路）**
1. `t_retrieval_decision` 建表 + 三档决策落库（`directReturn` 保持兼容，前端不用改）
2. `PromptBuilder` 换模板 + `temperature=0.2`
3. 失败分档（`RETRIEVAL_MISS` 不重试）

→ 产出：一组"决策分布 + 省下的调用数 + 重试率变化"的实测数，够写第 5 章一节。

**P1（一周，功能可感知）**
4. `t_ingredient_quantity_stats` 离线统计脚本（跑一遍历史 `t_dish_ingredient`）+ 校验接入
5. 依据校验 + `t_generation_attribution`
6. 推荐理由一句话

→ 产出：faithfulness 三比例 + 用量违反率对照（有/无统计化校验）。

**P2（选做，做对照实验才需要）**
7. `card_vector` + `bge-m3` + RRF 混合召回
8. 食材替代建议
9. 用户口味画像

→ 产出：BM25 vs 混合召回的 P@5 / 平均缺料数对照（正是你 PPT 第 7 页承诺的实验）。

## 六、几个必须注意的边界

1. **小模型是硬约束**。gemma4:e2b 上下文有限、指令跟随能力弱。上下文超过 ~1500 token 后，`format=json` 的遵守率会掉。所以"3 张卡 + 字段裁剪"不是优化，是必需。
2. **别在 Python 侧写业务库**。这是 Phase 1 定下的规矩（`ai-service` 只做推理）。索引构建、`card_vector` 写入、统计表生成，全部留在 Java 侧，Python 只暴露 `/embed` 与 `/generate`。
3. **向量化失败要能降级**。`/embed` 超时 → 退回纯 lexical，不能因为向量服务挂了检索就全挂。这跟现有 `DegradedModeGuard` 是同一套思路，别新起一套。
4. **三份文献不能用**：[6] PDF 损坏、[8]Majumder 文件名与内容不符、[9] PDF 文本层乱码。引用前务必换源核对，否则答辩被抽到会很难解释。
5. **别把 RAG 说成"我做了大模型微调"**。你做的是**检索增强的上下文构造 + 输出校验**，这个定位清楚反而是加分项——Brown 综述整篇都在说"上下文质量 > 模型规模"。
