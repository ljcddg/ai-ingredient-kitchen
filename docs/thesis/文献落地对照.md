## 二、四个真正改了代码的优化，具体是怎么落的

### 2.1 检索优先（[1] Brown 的 adaptive retrieval + [5] 谢广明的延时结论）

论文里的说法是"不是每个 query 都值得走完整 RAG 链路"。落到本项目：

| 档位 | 判据 | 动作 | 代价 |
|---|---|---|---|
| `DIRECT` | 缺料 0 且质量达标 | 直接返回库内菜品 | 检索级，**不调模型** |
| `RAG_GENERATE` | 有候选且满足率 ≥ 0.4 | 注入参考菜谱后生成 | 生成级 |
| `GENERATE_FRESH` | 无候选或满足率 < 0.4 | 裸生成（保底可用） | 生成级 |

证据：`es/eval/results-synergy.md` —— 仍需调模型的比例 93.2%（严格）/ 80.2%（宽松），
检索 P50 45.5ms vs 生成 P50 144.8s。`t_retrieval_decision` 按 query_hash 同时记 SEARCH 与 GENERATE 两条，
所以"省了多少次调用"是可查的，不是估的。

> 注意：`directReturn` 这个老字段**故意保留**，它是三档的兼容层。
> 答辩时说"三档替代了两态"要补一句"老字段留作兼容，值为 true 必然落在 DIRECT 档"。

### 2.2 结构化提示词 + 低温（[1] Brown 的 prompt policy）

原提示词是"一句话 + 附加要求"，改成固定分段：

```
【可用食材】→【硬约束】→【烹饪常识】→【参考菜谱】→【输出要求】
```

顺序是设计过的：越靠后越接近模型的下一步动作。烹饪常识放在参考菜谱**之前**，
否则模型容易照着参考的配方抄，把常识当废话。

低温 0.2 不是拍脑袋：小模型在菜谱这种"有客观答案"的任务上，温度高的收益是"措辞多样"，
代价是"用量乱跳"—— 而用量正是要卡的东西。

### 2.3 用量别靠固定上限（[8] Choi 的 KitchenScale）

论文用微调语言模型预测用量，拆成"计量类型分类 → 单位分类 → 数量回归"三个子任务。
本项目**不训练模型**（本地只有 gemma4:e2b，为一道菜的用量单独训回归头不划算），取它的统计版：

- `t_ingredient_quantity_stats`：同类别 × 同人数档的 P10 / P50 / P90（19 组 / 268 行）
- 参考菜谱把用量一起注入提示词 → 模型有可抄的数，比"凭空编 300g"好
- `grounding.py` 用 0.5~2 倍区间判"有据 / 偏离"

丢掉的是"计量类型 / 单位"这两级精度：分位数只回答"多少克"，不回答"该用勺还是用克"。
这一条在论文里应当写成"统计替代神经预测"，**不能写成"实现了 KitchenScale"**。

### 2.4 依据校验（[1] Brown 的评测缺口）

Brown 综述的结论之一是"评测仍以词面重叠类指标为主，检索与生成缺联合评测"。
`faithfulness` 就是补这个缺口：

| 档位 | 判据 | 含义 |
|---|---|---|
| `GROUNDED` | 参考里有同食材，用量 0.5~2 倍 | 有据 |
| `DEVIATED` | 有同食材但量差超 2 倍 | 有依据但被放大/缩小 |
| `UNGROUNDED` | 参考里没这个食材 | 幻觉嫌疑 |

`faith = grounded / 总数` 落 `t_ai_generation_record`。
**`faith` 为 NULL 表示判不了（没参考 / 参考没用量），不是 0 分** ——
统计必须 `WHERE faith IS NOT NULL`，否则冷启动的数据会把均值拖垮。

## 三、三处必须交代清楚的地方（答辩会被问）

### 3.1 [4][9] 未落地，理由要一句话说死

不是"没时间做"，是**做了也没有数据支撑**：
- [4] GNN 协同过滤：需要稠密的用户-菜品交互矩阵。本项目只有 2 个真实用户，
  图上一共几十条边，GNN 学出来的是噪声。
- [9] KG + 协同过滤：PDF 文本层是字库编码，无法解析原文；且本项目没有知识图谱
  （只有 `t_dish_tag` 的扁标签），硬造一个 KG 只是为了"看起来用了图方法"。
  替代做法 `IngredientDirectory` 只解"西红柿/番茄"这种同名不同字，不解语义相似 ——
  这一点要如实说，别把它包装成"实现了语义增强"。

### 3.2 [7] 的"双视角"只落了一半

Li 2023 的核心是"口味偏好"和"健康度"两个视角联合。本项目健康侧有
（`NutritionCalculator` 按成分表算、营养展示、能量千卡参与排序），
口味侧 `TasteProfileSignal.score()` **恒返回 0.5（中性）**。

原因写在代码注释里：现有 `t_user_ingredient_pref` / 收藏 / 评分都是合成数据，
接上去能做出"个性化有效"的假象，但站不住。这是**主动不做**，不是遗漏。

### 3.3 [10] 只用了图像，没有用图像特征

宋亚光的做法是把食物图像特征送进异构图表征。本项目：
图像 → YOLO 识别成食材 → 厨房页回填 → 走普通检索。
**图像特征没有进 ES 召回**，也没有图模型。当前权重还是 COCO 预训练，
能对上库内的只有 carrot → 胡萝卜、broccoli → 西兰花 两类。
这一条在论文里只能写"以图取食材"，不能写"多模态召回"。
