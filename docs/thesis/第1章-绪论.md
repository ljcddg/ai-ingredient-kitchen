# 第1章 绪论

## 1.1 选题背景

晚上七点回到家，打开冰箱一看，里面只剩下两个番茄、几个鸡蛋和半块豆腐，“今晚吃什么”这个问题每天都得回答一遍，对不少独居青年和双职工家庭来讲并不轻松。愿意自己动手做饭的人其实在慢慢变多，一是外卖的口味越来越标准化，二是价格和食品卫生方面的顾虑也把人重新推回了厨房。可是真的下了厨才会发现，做饭的门槛常常不在于“会不会做”，而在于“现在能做什么”，菜谱平台上收录的菜式有几万道，用户遇到的并不是选择太少，而是不清楚冰箱里剩下的这几样食材到底能撑起哪一道菜。

现有的两类工具，都没能很好地接住这个问题。传统菜谱应用说到底是“内容库加搜索框”，用户要先把“我有什么”翻译成“该搜什么”，再一篇篇点开核对配料，挑选和比对的负担全都压在用户这边；通用对话式大模型倒是能聊着天生成一份菜谱，却看不到用户手边有什么，输出也不够稳定。在开发过程中，本文作者做过一组实测，让本地小模型估算一道菜的营养，再按食材成分表逐项复算，两者相比平均偏差达到 181.79%，最大的一例有 825.93%；提示词不加约束时，模型还会给出“料酒 300 g”这样明显不合常识的用量。更麻烦的是，这些不可信的内容一旦沉淀到公共菜库，就会被后面的检索和推荐反复取用，错误没有被纠正，反而被放大了。另外，生成一道菜谱的本地推理实测 P50 约 144.8 秒，这里面还含着排队时间，而一次食材检索只需 45.5 毫秒上下，让用户盯着转圈等不现实，把所有请求都交给生成更不现实。

近两年，技术方面的条件变化得很快。推荐系统从协同过滤、矩阵分解走到深度学习方法，评价体系和工程实践都比较成熟了；检索增强生成（Retrieval-Augmented Generation，RAG）给模型配上外部知识源，相当于让它“开卷考试”，在很多知识密集型任务上都明显减轻了幻觉，而且更新知识只要替换索引，不必重新训练模型[1]；本地推理框架则让几十亿参数的小模型在个人电脑上运行变成现实，隐私和调用成本都能控制住。不过检索和生成这两套能力长期各自发展，前者回答“库里有什么”，后者回答“模型知道什么”，却很少有人回答这样一个问题：以用户现有的食材来看，此刻最值得做哪一道，值不值得再让 AI 现做一道。

本课题就是由此立项的，主要工作是研发一套“面向家庭食材利用的智能菜谱推荐与生成系统”，把“手边的食材能否支撑起一道菜”当作推荐排序和内容生成共同的约束，让检索、生成和质量控制在同一个系统里互相配合，而不是像过去那样各管一段，彼此都不知道对方的存在。

## 1.2 选题意义

本课题的意义，可以从方法和现实这两个层面来看。

在方法层面，第一点是它把排序目标从“猜你喜欢”改写成了“此刻做得出来”。主流推荐都以偏好匹配为核心，主要看评分、点击和收藏；本文则把“可制作性”，也就是菜谱必需主料的齐备程度，提升为一等信号，把评分和互动这类社交证明降到次要位置。这不是简单调一下权重，而是把排序问题从兴趣匹配改写成可行性判断，对同样带有物理条件约束的场景，比如食材、厨具和时长，有一定的通用参考价值。第二点是它把生成质量拆成“格式合格”和“约束合格”两层分别记录，前者看模型有没有按约定的结构输出，后者看模型有没有听从用户给的条件，像必用、禁用、用量和设备这些。这两类失败改进的方向完全不同，混在一起只算一个“失败率”，会一直把优化方向带偏，这种分档思路也可以推广到其他受约束的生成任务。第三点是它把“什么时候值得让 AI 现做一道”变成可以度量的问题，通过记录模型调用比例、排队和推理耗时，尽量用便宜的检索兜底，把昂贵的生成留给检索确实解决不了的请求，相当于把 RAG“检索优先”的思路反过来用。

在现实层面，对用户来说，系统把“做决定”变成了“照着做”，每道菜都标出食材档位，也就是“齐活”“差一点”还是“缺得多”，同时给出缺料清单，不管直出还是不直出都说明原因，选择起来比一篇篇比对省事得多。对平台来说，生成的内容要经过校验才能沉淀回公共菜库，菜库越厚，直出率越高，模型调用就越少，慢慢形成“用得越多越省”的闭环，而检索与生成之间两个数量级以上的耗时差，决定了这笔权衡直接关系到系统能不能长期跑得动。对工程实践来说，整套系统可以跑在个人设备上，也就是本地模型加单实例微服务，数据不出本机，适合对隐私敏感的家庭场景；用到的 Spring Cloud、Elasticsearch 和 Vue 都是成熟的开源技术栈，复现门槛不高，开发中踩过的坑，比如 Elasticsearch 的 terms 查询默认是“或”不是“与”、雪花 ID 必须序列化成字符串，对同类的毕业设计也有借鉴意义。

## 1.3 国内外研究现状

本节按“推荐系统总体进展”“食物与菜谱推荐”“大模型与检索增强生成”三条线索梳理国内外的研究，说明各类工作做到了什么程度、有哪些共同问题，最后给出本课题遵循的评价标准。

### 1.3.1 推荐系统研究进展

推荐系统作为一个独立的研究方向，已有二十多年。Ricci 等人主编的《Recommender Systems Handbook》对协同过滤、基于内容和混合策略这些经典范式做了比较系统的整理[2]，评分预测用的 RMSE/MAE，还有 Top-K 推荐用的 Precision@K、Recall@K、NDCG，也在这段时间里慢慢成为通用评价指标。深度学习进入推荐领域之后，模型结构从宽深网络发展到序列建模和图神经网络，可以利用的特征越来越丰富；Li 等人的综述进一步指出，大模型带来的变化不只是结构上的，而是把“用户—物品匹配”从判别式打分改写成了生成式建模，优势在于世界知识、自然语言理解和推理能力，与此同时，基准设计、模型鲁棒性和部署效率也成了新的开放问题[3]。国内方面，项亮写的《推荐系统实践》覆盖了协同过滤、隐语义模型和工程实现，是这个领域流传最广的入门书[4]；谢广明等人针对大语言模型与推荐的结合做了系统综述，梳理出六个切入点，认为语义 ID 化减轻了传统 ID 表征泛化性差的问题，“预训练加提示”的范式降低了多场景适配成本，对话式推荐让结果变得可以解释，同时明确指出推理延时是工业落地最大的障碍，幻觉和数据隐私是可信度上的两个隐患[5]。

总的来看，这个领域的排序准确率指标已经趋于一致，研究重心开始转向覆盖率、多样性和冷启动；不过绝大多数工作都只把“用户的历史行为”当作唯一输入，对“用户此刻手里有什么”这类物理条件没有什么感知。

### 1.3.2 食物与菜谱推荐研究进展

国外方面，Mahajan 和 Kaur 的系统综述把 2006 年到 2023 年的食物推荐文献梳理了一遍，按过滤技术、方法、功能和数据源分类，结论是食物推荐长期以来都以健康和营养管理作为重要牵引，但在技术落地上还明显不够[6]。方法层面，Li 等人在食物知识图谱上用图神经网络做推荐，把“用户偏好”和“食谱健康度”两个视角结合起来，在包含 18 万菜谱、70 万交互的真实数据上验证了口味和健康可以兼顾[7]；生成这一侧，Majumder 等人提出个性化菜谱生成任务，把用户历史偏好的技术级和菜谱级表示通过注意力融合层注入文本生成过程，生成的菜谱比非个性化基线更合理，也更贴合个人口味[8]。国内方面，耿化聪等人把菜谱的实体和关系嵌入不同的向量空间，用语义相似度增强协同过滤，缓解了数据稀疏和冷启动问题，召回和 AUC 都有提升[9]；宋亚光等人进一步把用户、食谱和食材组织成异构图，引入跨模态多视角的自监督任务，在公开食物推荐数据集上，AUC、NDCG@10、Recall@10 相比最优基线分别提升了 6.35%、8.13% 和 11.7%[10]。

这个方向的方法、数据和指标都已经相当成熟，各种纪录还在被不断刷新；但绝大多数工作回答的都是“你可能喜欢”，而不是“你现在做得出来”，用户手边食材构成的硬约束，在现有模型里最多只作为一个普通特征存在。

### 1.3.3 大模型与检索增强生成研究进展

Lewis 等人提出的 RAG，把预训练的 seq2seq 模型当作参数化记忆，把维基百科的稠密向量索引当作非参数化记忆，再用神经检索器把两者端到端地结合起来，在 Natural Questions、TriviaQA、WebQuestions 这些开放域问答任务上刷新了当时的最好成绩，生成任务上也更具体、更多样、更符合事实；它的“换掉索引就能更新知识”以及可以溯源这两个特点，被后来的研究反复提到[1]。Li 等人关于生成式搜索与推荐的综述，把这一范式概括成“用生成的方式解决匹配问题”，并指出评测基准、模型鲁棒性和部署效率是三个还没解决的问题[3]。在烹饪场景里，Majumder 等人已经证明用户的历史偏好可以有效控制菜谱文本的生成走向，说明生成式方法在菜谱领域是行得通的[8]。

问题在于，直接让通用大模型生成菜谱的做法已经很多，共同的毛病也很明显，一是格式漂移，输出常常裹着 Markdown 代码块，或者干脆缺字段，二是约束违反，格式看着完美但并不遵守用户给的条件，三是用量幻觉。谢广明等人也把幻觉列成大模型进入推荐系统时主要的可信度风险[5]。而 RAG 现有的用法基本都是“先检索、再生成”这样的单向流水线；在菜谱场景里，反过来定量地回答“先检索到什么程度就不必再生成”，也就是把生成的机会成本算清楚，这类工作还很少。

### 1.3.4 存在的问题与本文采用的评价标准

把这三条线索合在一起看，现有研究和家庭“食材利用”这个场景之间一共存在四个缺口。第一个是推荐目标错位，排序优化的目标是“猜你喜欢”，可用户真正的问题是“我现在到底做不做得出这道菜”，后一个问题可以用缺料数量直观地度量，前一个问题对此却没有感觉。第二个是生成的可控性还停留在格式这一层，JSON 合法并不等于内容合规，必用、禁用、用量、设备和时长这类业务约束还缺少系统性校验，失败时也缺少分档归因。第三个是检索和生成彼此割裂，两类模块各自优化也各自评测，缺少一种以“模型调用成本对照检索质量”为目标的统一权衡，结果系统要么全靠检索，覆盖不够全，要么全靠生成，算力又浪费。第四个是评价口径和实际有些偏离，排序类研究报 Precision@K、NDCG，生成类研究报 BLEU、困惑度，缺少对“可制作性”和“可操作性”的人工评价，也缺少端到端资源开销的报告。

针对上面这些缺口，本课题采用下面的评价标准，它们和第 5 章的实验一一对应。

排序效果方面，固定测试集按食材组合的哈希划分验证集和测试集，防止同一输入的变体跨集合泄漏；主要指标用 Precision@5 和平均缺失主料数，失败样本不剔除，免得用丢掉失败样本的办法把结果弄得好看。

生成质量方面，格式通过率、约束违反率和重试成功率都分档统计，分母是实际送检的输出总量。

人工评价方面，邀请至少 2 名评价者做盲评，策略标签只写在不公开的答案键里，对可操作性、配料与步骤的一致性、请求符合度分别打分；评价者之间的一致性用线性加权的 Cohen's kappa 度量，只有一个人评分时就明确说明“不计算一致性”，不用主观分替代客观指标。

系统与资源方面，排队耗时和推理耗时分开统计，报告 P50/P95、模型调用比例以及端到端总耗时；另外还设置了故障场景下的状态一致性测试，包括 Elasticsearch 中断、服务重启、取消和完成并发这几种情况。

## 1.4 课题研究内容

围绕“让用户以自己的手边食材为起点，用比较低的门槛得到一道做得出来、又信得过的菜”这个目标，本课题的研究内容可以分为三项。

（1）以食材可制作性为核心的推荐策略。首先要建立一条食材归一的链路，把正式名和别名统一登记起来，名字冲突时以正式名为准；然后以“全部非调料食材”定义菜谱的必需主料集 R，和用户手边的集合 U 一起算出满足率和缺料，区分出“差一点”和“缺得多”两档，并输出可以执行的缺料清单，而不是一个抽象出来的分数。召回层要支持主数据 ID 和表外名称两条路查询，否则用户自己输入的食材谁都搜不到。排序层先做硬过滤，把时长、难度、人数不合适的结果滤掉，再做加权合成，匹配占 0.45、质量占 0.30、情境占 0.15、个性化占 0.10 作为占位，质量分用威尔逊下界来抵抗刷分。对满足直出规则的结果，也就是覆盖率不低于 0.8、评价人数不少于 10、威尔逊分不低于 0.84 的，就直接返回；不满足时也返回最接近的那道菜，同时给出可以解释的未直出原因，引导用户转到生成分支。

（2）面向用户条件的生成与校验。在“系统提示词、约束解码（format=json）、应用层字段校验”这三道防线之外，再增加第四道业务约束层，必用和禁用的食材都按归一化之后的食材 ID 比对，避免“鸡蛋面”被当成“鸡蛋”；用量按“食材类别乘人数”设定上限，而不是拿一个固定阈值套在所有场景上；步骤和配料表要互相印证，步骤里出现的食材必须能在配料表里找到，必用的食材也必须在步骤里有它的用途。自相矛盾的约束在提交阶段就直接拒绝，不让用户白等好几分钟。格式和约束的合格情况分档落库，方便做归因分析；校验不合格时把具体原因拼回提示词，有限地重试一次，超过次数就判定失败，同时保留记录。生成前先检索相似菜谱作为参考上下文注入提示词，并记录参考菜谱的 ID，这其实就是把 RAG 的思想用在生成增强上；营养值按食材成分表在本地计算，克重覆盖率不低于 0.8 才采用，否则保留模型估算并标注来源。

（3）工程可靠性与资源权衡。自建一个内存任务队列支撑异步生成，做到排队可见、可以调序、可以取消，单个用户的排队上限设为 5，并发度做成配置项；任务的状态迁移用数据库条件更新实现，保证“取消”和“完成”并发时只产生一个合法的终态，任务和结果之间再加唯一约束，防止重复落库。坚持检索优先、生成兜底，Elasticsearch 不可用时检索就降级成空列表，把用户引导到生成分支，而不是把全部请求都砸向本地模型；索引同步放在事务提交之后，用领域事件加待办表的方式退避重试，间隔是 5、15、45、120 秒，同时保留每日的全量核对和幽灵清理。注册链路用布隆过滤器做前置判存，Redis 出故障时降级为直接查库，缓存不可用并不等于服务不可用。

## 1.5 论文章节组织

本文一共分为六章。

第 1 章是绪论。交代选题的背景和意义，梳理国内外的研究现状并指出存在的缺口，说明评价标准、研究内容以及全文的组织安排。

第 2 章是需求分析与总体设计。从家庭食材利用这个场景出发，定义用户角色和功能约束，给出网关、账号、菜品、公共四个模块的 Spring Cloud 总体架构、核心数据模型和部署边界，并说明各外部依赖出故障时的降级策略。

第 3 章是关键方法设计。详细给出食材归一与满足率模型、缺料惩罚与排序合成、直出规则与未直出解释、四层生成校验规则，以及参考菜谱增强和营养计算的口径。

第 4 章是系统实现。按模块说明认证与布隆过滤器、任务队列与状态机、检索的双路召回、发布与索引同步补偿、候选食材审核，以及管理端和前端这两种消费形态的实现要点。

第 5 章是测试与实验。介绍固定测试集的构建方法，报告排序对照、生成质量分档、检索与生成协同、系统负载、故障恢复这些实验的结果，并如实交代样本规模和口径上的局限。

第 6 章是总结与展望。归纳已经完成的工作和实际验证到的边界，指出单实例队列、轮询交互、个性化信号暂时留空等待真实数据这些不足，以及后续可以改进的方向。
