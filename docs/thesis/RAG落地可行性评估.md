## 三、本次已实现的三条（P0）

### 3.1 三档决策

| 档位 | 触发 | 动作 | 代码 |
|---|---|---|---|
| `DIRECT` | 缺料 0 且质量达标 | 直接返回，不调模型 | `RetrievalDecision.decide()` |
| `RAG_GENERATE` | 有可用候选且满足率 ≥ 0.4 | 带参考生成 | 同上 |
| `GENERATE_FRESH` | 无候选或满足率 < 0.4 | 裸生成 | 同上 |

`DishRecallResult` 新增 `decision` / `decisionHint`，`directReturn` 保持兼容（前端第一批改造不用改）。

**日志双来源**：`source=SEARCH` 记召回侧判定，`source=GENERATE` 记生成时真正注入了几条参考。
两者用 `query_hash` 关联 —— 判了 `RAG_GENERATE` 却在生成时变成 0 条参考，就是"判了没做到"，
不分开记会把这种情况统计成"判定正确"，直出率虚高。

### 3.2 提示词五段

```
【可用食材】番茄(ID:101)、鸡蛋(ID:102)
【硬约束】
- 必用：番茄
- 总耗时不超过 30 分钟（备菜 + 下锅）
- 人数：2 人
【参考菜谱】（库内相似菜，只作灵感，不是答案）
1. 番茄炒蛋｜口味：家常｜耗时约 15 分钟｜主料：番茄、鸡蛋
【输出要求】只输出一个 JSON 对象……
```

两个细节是刻意做的：

- **输出要求分两版**：有参考时允许"来自【可用食材】或【参考菜谱】"，没参考时只能来自【可用食材】。
  否则模型会去找一段不存在的参考（这条是写测试时被断言抓出来的）。
- **参考段整段消失**（不是留空标题）：两臂对照实验的差别必须干净。

### 3.3 失败分档

`kind` 说哪一类失败（超时 / 校验耗尽），新增 `tier` 说校验耗尽里卡在哪：

| tier | 判据 | 该改什么 |
|---|---|---|
| `FORMAT_FAIL` | JSON 解析失败 / 只有格式问题 | 提示词或约束解码 |
| `CONSTRAINT_FAIL` | 有约束类问题 | 约束表达、回注具体项 |
| `retrieval_miss`（标记位） | 本次生成没有任何参考 | 不计入 RAG 效果统计（冷启动的代价） |

> 关于方案里"`RETRIEVAL_MISS` 不重试"：**本次没有实现跳过重试**。
> 原因是当前"无参考生成"是常态（菜库还小），把它一律当检索未命中而不重试，
> 会把正常的约束重试也砍掉。先把分档记下来，等 `t_retrieval_decision` 有了统计再决定阈值。

## 五、建议的下一步顺序

1. **补证据**（零风险）：跑一段时间，用 `t_retrieval_decision` 出"档位分布 / 直出率 / 回退率"三个数。
2. **faithfulness 对照**：`t_ai_generation_record.faith` 已落库，按 `reference_dish_ids` 是否为空分组，
   就能回答"带参考生成到底有没有更可信"——这是第 5 章最硬的一组数据。注意 `WHERE faith IS NOT NULL`。
3. **知识库分组实验**：按 `knowledge_rule_ids` 分组比对 `faith` 与人工评分，判断哪几条常识真有用。
4. **ES 起来后**：重跑 `es/eval/` 那四组实验（现有结论绑在 32 道菜的旧快照上）。
5. #5 向量档与 #8 口味画像**等有真实数据再碰**，不要为了"功能列表好看"去做没有数据支撑的模块。
