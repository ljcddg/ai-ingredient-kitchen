## 一、认证与网关（简历第 1 条）

### 简历原文
> Gateway 统一入口，前缀匹配路由和白名单放行，JWT 校验通过后清理外部传入的 userId 防止伪造；注册接口通过数据库唯一索引保证用户名和邮箱唯一，Redis 缓存已注册用户名做快速拦截，避免每次注册都查库；

### 面试官会怎么问

| 层级 | 问题 | 考察点 |
|---|---|---|
| L1 | 为什么要在网关做鉴权而不是在每个服务里做？ | 微服务治理认知 |
| L2 | `GlobalFilter` 和 `RouteFilter`（`Ordered`）有什么区别？为什么 filter 要配 order？ | Spring Cloud Gateway 源码理解 |
| L3 | 路由前缀怎么剥离的？白名单写的是带前缀还是不带前缀的路径？ | 真实踩坑经历 |
| L4 | 你说"清理外部传入的 userId"，为什么必须清理？清理完写什么？ | 安全意识 + 顺序 |
| L5 | 白名单里有哪些路径？为什么 `/rank` 不放行？ | 鉴权粒度设计 |
| L6 | JWT 的密钥存在哪？多个服务怎么保证一致？密钥泄漏怎么办？ | 密钥管理 |
| L7 | 布隆过滤器和数据库唯一索引，哪个是最终保障？为什么两个都要？ | 理解"概率型结构 + 确定性兜底" |
| L8 | 布隆过滤器误判了（说不存在但实际存在），会怎样？ | 概率型结构的正确用法 |
| L9 | 布隆过滤器**说存在**但实际不存在（反向误判）会怎样？ | 是否真懂 BF 的单向性 |

### 完整答法

**Q：为什么在网关统一鉴权？**

> 一是**收敛**：JWT 解析逻辑只在网关写一次，account 和 dish 不各自实现一遍，避免 N 处代码 N 种行为；
> 二是**减少服务暴露**：account(8081)、dish(8082) 在内网，网关(7000) 是唯一对外入口，攻击面小；
> 三是**可演进**：以后加限流、加灰度、加 IP 黑名单都在网关这一层做，不用改业务代码。

**Q：`GlobalFilter` 和 `RouteFilter` 什么区别？为什么配 order？**

> `GlobalFilter` 对**所有请求**生效，路由转发本身也是它内部的一个 `NettyRoutingFilter` 完成的；`RouteFilter` 只在命中特定路由（`RoutePredicate` 匹配上）时才执行。
>
> 关键在 order：我这个 JWT 过滤器必须**早于路由转发**执行，否则 token 还没解出来请求就已经转发出去了。所以要 `implements Ordered` 并返回 `getOrder() = -100`（取负值是为了排在 Spring Cloud 内置的 `NettyRoutingFilter`（`Ordered.LOWEST_PRECEDENCE`，即 `Integer.MAX_VALUE`）之前）。用负数不用 0，是因为 0 可能和别的前置过滤器撞顺序。

**Q：前缀怎么剥离？白名单写带前缀还是不带？**

> 用的是 Spring Cloud Gateway 内置的 `StripPrefix=2` 过滤器——因为路由是 `/api/dish/**` → `lb://dish-service`，`/api/dish` 是两段（网关前缀 + 服务名），所以剥 2 段，下游收到的是 `/search`。
>
> **这里我踩过一个坑**：白名单一开始写成 `/api/account/auth/**`，结果永远匹配不上。原因是我代码里判断白名单时，是先把路径按 `STRIP_PREFIXES` 还原成"下游视角"（`/api/account/auth/login` → `/auth/login`）再拿去 `AntPathMatcher` 匹配的，所以白名单必须写**剥掉前缀之后**的路径：`/auth/**`、`/actuator/**`、`/favicon.ico`。
>
> 另外代码里那个 `STRIP_PREFIXES` 列表（`/api/account`、`/api/dish`、`/api/product`、`/api/order`）只用于白名单匹配，**真正剥离走的是 gateway.yaml 里的 `StripPrefix=2`**，两个别搞混。

**Q：为什么必须清理外部传入的 userId？**

> 因为 `X-User-Id` / `X-Username` 这两个头是网关和下游服务之间的**内部身份传递通道**。下游服务不解析 JWT，它信任这两个头。
>
> 如果网关不先删就直接覆盖还算好，但如果代码写的是"有值就沿用、无值才写入"，攻击者只要 `curl -H "X-User-Id: 1"` 就能冒充任意用户。我的实现是**先 `headers.remove()` 掉外部传入的，再 `.header()` 写入自己从 JWT 解析出来的值**——顺序反了就等于没做。

**追问：那 reject 时怎么返回？**

> 这里也有坑：只 `setStatusCode(401)` 是**无效的**，因为响应体没写，前端拿到的是空 body。正确做法是 `setStatusCode(HttpStatus.UNAUTHORIZED)` + `setContentType(MediaType.APPLICATION_JSON)` + `charset=UTF-8`，然后 `response.writeWith(Mono.just(buffer))` 写 `Result.unauthorized(msg)` 的 JSON。这样前端才能弹出"登录已过期"。
>
> 中文乱码也要管：编码漏了 UTF-8，中文提示在浏览器里就是乱码，所以序列化失败时我还留了一个硬编码的兜底 JSON，确保任何情况下 body 都有内容。

**Q：JWT 密钥怎么管？多服务怎么一致？**

> jjwt 0.12.5，`JwtUtil` 放在 common 模块里做成**纯静态工具类**，各服务自己 `@Bean` 注入密钥。
>
> 这里踩过一个非常典型的坑：gateway 和 account 的 `jwt.secret` **必须逐字一致**，差一个字就全线 401，而且报错信息是"token 解析失败"，很难定位。所以我把它做成了**可注入的环境变量** `JWT_SECRET`，本地默认值写在各自 `application.yml` 里，开发和部署用同一份。
>
> 有效期 2 小时。密钥泄漏的防护：密钥不进代码库（只走环境变量）、后续可以升级成非对称签名（RS256，私钥只给网关，公钥下发到各服务），这样各服务只能验签不能签发。

**Q：布隆过滤器和唯一索引，哪个是最终保障？为什么两个都要？**

> **数据库唯一索引是最终保障**，布隆过滤器是性能优化。
>
> 布隆过滤器是**概率型**结构：它只能"说可能存在"，不能"说一定存在"（有假阳，代码里 `FALSE_PROBABILITY = 0.01`）。所以它只能用于**否定**路径：登录时"这个用户名一定没注册过"→ 直接拒，不用查库。而注册时"可能存在"→ **必须查库确认**，然后最终 insert 时靠数据库唯一索引兜住并发（两个请求同时过了布隆和查库，都会走到 insert，索引保证只有一个成功）。
>
> 容量设计：预期插入 100 万，误判率 0.01。

**Q：布隆过滤器误判了会怎样？反向误判呢？**

> 布隆过滤器只会**假阳**（说存在实际不存在），不会**假阴**（说不存在实际存在）——只要元素加进去过，就永远不会被判为不存在，因为那个 bit 位只会置 0 不会清 0。
>
> 这正好对应两条铁律：
> - **"说不存在" 100% 准确 → 可以直接拒，不查库**（登录前置过滤）
> - **"说存在" 可能误判 → 必须查库**（注册确认）
>
> 反过来说，如果误判导致"明明没注册过的用户名被拒绝"，用户体验上是一次可重试的失败，概率 1%，可接受；而如果假阴（漏掉已存在的用户），就是安全漏洞，绝对不能发生。BF 的性质正好保证不会发生。

## 二、缓存降级（简历第 2 条）

### 简历原文
> Redis 不可用时查 MySQL，写入跳过缓存并记录告警日志；服务恢复后启动阶段将中断期间的用户数据重新加载至 Redis，保证缓存最终一致；

### 面试官会怎么问

| 层级 | 问题 | 考察点 |
|---|---|---|
| L1 | 为什么用布隆过滤器而不是 Redis Set / Caffeine？ | 空间成本意识 |
| L2 | 写失败为什么不抛异常？ | 是否理解事务边界 |
| L3 | 降级时读失败你返回什么？返回 false 会怎样？ | 降级方向的判断 |
| L4 | 30 秒冷静期是什么？为什么需要？ | 防止故障放大 |
| L5 | pendingWrites 什么时候 flush？为什么没有定时任务？ | 设计取舍 |
| L6 | 启动时怎么知道要回填多少数据？ | 数据一致性思路 |
| L7 | 如果 Redis 故障期间有人注册，服务又重启了，pendingWrites 丢了怎么办？ | 极端场景 |
| L8 | "最终一致"这里有多久？你能保证吗？ | 诚实度 |

### 完整答法

**Q：为什么用布隆过滤器而不是 Redis Set？**

> 因为**空间成本**。Set 要存完整用户名，一个用户名按平均 10 个字符算，100 万用户就是几十 MB；布隆过滤器只存位数组，100 万容量 / 0.01 误判率大约 **1.2MB**，差了两个数量级。
>
> 更重要的是**它解决的是不同的问题**：我要的不是"快速拿到完整用户名列表"，而是"**快速判断某个用户名肯定没被注册过**"——这是一个否定判断，布隆过滤器天生擅长，而且**不需要存原始值**。
>
> 代价我也认：它有假阳、删不掉（`add` 之后无法 remove）、不保证一致性。所以我只把它用在"能容忍假阳"的位置。

**Q：写失败为什么不抛异常？**

> 这是**被事务逼出来的**。`register` 方法上有 `@Transactional(rollbackFor = Exception.class)`，Redis 写发生在 `save()` 之后。如果这里把异常抛出去，整个事务回滚——**用户明明注册成功了，因为缓存写不进去就注册不上了**，这是把一个"缓存问题"升级成了"业务不可用"。
>
> 所以我的处理是：catch 住异常 → 把用户名塞进 `pendingWrites`（`ConcurrentHashMap.newKeySet()`，并发安全）→ 记 warn 日志 → **正常返回**。主流程无感，缓存的缺口异步补。

**追问：那你打算什么时候补？**

> 两个时机，形成双保险：
>
> **① 运行时顺手补**：`flushPendingWrites()`，在 `add` 和 `mightContain` 拿到 filter 对象之后都会调一次。Redis 恢复后，只要有任何一次注册或登录操作进来，就顺手把待写清单刷回去。好处是**零额外开销**，不需要定时器。
>
> **② 启动时全量校准**：`warmUp()`，服务启动时执行。这里有个设计细节——**不是简单地判断"count() > 0 就不预热"**，而是拿 `filter.count()` 和 `userMapper.selectCount(null)` **两个数比对**，估算数量少于库里记录数就判定不完整，重新全量灌一遍（`add` 是幂等的，重复加无副作用）。
>
> 为什么必须要有第 ② 道：pendingWrites 是**内存**的，Redis 故障期间注册了用户、然后服务重启 → 内存队列丢失 → 这些人既不在索引里、也不在 pendingWrites 里，就永久漏了。启动校准是唯一的兜底。失败只 `log.warn` 不阻塞启动（Redis 还没起来也得让人能进服务）。

**Q：降级时读失败返回什么？返回 false 会怎样？**

> **返回 true**（`mightContain` catch 里 `return true`），然后调用方就会去查数据库。
>
> 如果返回 false，语义是"这个用户一定没注册过"——登录接口会**直接抛"用户名或密码错误"**。用户明明注册过，却因为 Redis 挂了就登不进来，这是**把缓存故障放大成了业务不可用**，是最糟的降级方向。
>
> 所以降级原则是：**宁可多查一次库，绝不误拒一个真实用户**。缓存故障的代价是 QPS 打到 MySQL（还能扛），而不是业务不可用。

**Q：30 秒冷静期是什么？**

> `DEGRADE_COOLDOWN_MS = 30_000`。进入降级后记一个时间戳，30 秒内**不再重复尝试** Redis 连接。
>
> 原因是 Redis 挂掉时，每次 `mightContain` 都抛异常 → 每次都建连接 → 连接池被瞬间打满 → 雪崩加剧。有了冷静期，30 秒内所有请求都**无脑走 MySQL**，不再碰 Redis，给连接池喘息时间。
>
> 日志文案是 `布隆过滤器[{}] {}失败，未来 {} 秒降级为直查数据库（原因：{}）`，把"为什么降级"和"降级多久"都打出来，避免事后排查时抓瞎。

**Q："最终一致"有多久？能保证吗？**

> **我不敢说绝对保证，说清边界**：
>
> - Redis 正常时：注册成功立即 `add`，**强一致**；
> - Redis 故障期间：新注册的用户**不在布隆里**。影响是"登录时会多查一次库"（因为 `mightContain` 返回 false → 直接拒）。
>
> 等等，这里我需要更正——实际上故障期间读也失败了会返回 true 走查库，所以**登录不受影响**。真正的风险窗口是"Redis 恢复但 pendingWrites 还没 flush"这段，此时新用户不在布隆里 → 登录被误拒。
>
> 这个窗口的兜底就是 `flushPendingWrites()`：Redis 一恢复，第一次 `add` 或 `mightContain` 就会把待写清单刷回去。**所以故障恢复后，缺口在第一次访问时就会被补上。**
>
> 极端场景（故障期注册 + 立即重启）靠启动 `warmUp()` 全量校准。所以是"最终一致"，窗口是"Redis 恢复到下一次访问之间"。

**Q：为什么布隆过滤器注入 `UserMapper` 而不是 `UserService`？**

> 因为 `UserServiceImpl` 也依赖 `UserBloomFilter`（注册时要 `add`）。如果 `UserBloomFilter` 再注入 `UserService`，就形成 **Bean 循环依赖**，Spring 启动直接失败。
>
> 解决办法是**依赖倒推到底层**：`UserBloomFilter` 只依赖 `UserMapper`（MyBatis Mapper 不依赖 Service，安全）。需要查库时用 `userMapper.selectCount` / 直接查用户名是否存在，绕开了 Service 层。

## 三、菜谱检索（简历第 3 条）

### 简历原文
> 食材 ID 走精确匹配，菜品名和自由文本使用IK分词模糊查；召回后应用层判断是否命中，命中直接返回，减少不必要的推理开销，否则触发模型生成；

### 面试官会怎么问

| 层级 | 问题 | 考察点 |
|---|---|---|
| L1 | 为什么先检索再生成？省的是什么？ | **★ 本项目核心决策** |
| L2 | 直出率多少？怎么衡量的？ | 是否量化 |
| L3 | 为什么不用 ES 的 `match` 查询？精确匹配不够吗？ | 召回与精排的分工 |
| L4 | ES 的 `terms` 是 AND 还是 OR？ | **★ 高频陷阱题** |
| L5 | 排序怎么做的？为什么 ES 只粗排？ | 架构分层认知 |
| L6 | 什么叫"命中"？阈值怎么定的？ | 判定标准 |
| L7 | 威尔逊下界是什么？为什么不用平均分？ | **★ 高频** |
| L8 | `minimum_should_match` 放在哪一层？ | DSL 细节 |
| L9 | `status` 字段为什么必须放 `filter` 而不是 `must`？ | 安全/数据泄漏意识 |

### 完整答法

**Q：为什么先检索再生成？**

> 因为**检索和生成的成本差了两个数量级**。本地模型生成一道菜 12~26 秒，检索是毫秒级。而且从业务上讲：**这道菜如果已经存在且质量达标，用户要的恰恰是"这道菜"，不是"再生成一道新的"**。
>
> 更关键的是**飞轮效应**：AI 生成的菜经校验发布后进公共菜库 → 下次有人用同样的食材 → 直接命中 → **不需要再调模型**。所以菜库越厚、直出率越高、AI 调用越少。
>
> 我实测过这个收益：排序实验里 P@5 从 0.339 提升到 0.467，而直出率提升带来的模型调用下降是**几个数量级**的（生成一次 20 秒 vs 检索一次 20 毫秒）。

**Q：`terms` 是 AND 还是 OR？（高频陷阱题）**

> **默认是 OR**。这是 ES 最容易踩的坑之一。
>
> 我要表达"这道菜必须包含用户选的**所有**食材"，如果写成 `{"terms": {"ingredientIds": ["1","2","3"]}}`，ES 的语义是"包含 1 **或** 2 **或** 3"——结果会召回一堆只用了其中一种食材的菜。
>
> 正确写法是每种食材拼一个独立的 `term` 子句，全部放进 `must`（AND 语义）。我在 `EsDslBuilder.buildIngredientClause()` 里专门处理了这件事，类注释里也写了原因，因为这个坑**看起来完全正常，跑出来的结果也"像对的"**，不对比就发现不了。
>
> 顺带说，我们这个场景的召回口径是 **"至少命中一样"**（`bool.should` + `minimum_should_match=1`），"全部包含"是应用层精排阶段的事——因为**还要算缺料数、满足率**，光靠 ES 表达不了。

**Q：为什么不用 `match`（分词）？精确匹配不够吗？**

> **够，而且必须精确**。这里有个业务前提：菜谱检索是**"手上有这几样食材，能做什么"**，本质是**主键 ID 的集合运算**，不是文本搜索。
>
> 如果用分词匹配，`"排骨"` 和 `"排"` 会被切成有交集，搜"排骨"召回"里脊肉"的菜——这在文本搜索里是合理的（召回宽一点），但在**食材匹配**场景是**错误的**（用户没有排骨，就不该看到排骨的菜）。
>
> 还有一个实现层面的理由：我们**不引 Spring Data ES**，直接用 `RestClient` 手发 JSON DSL。这样索引 mapping 只有一份唯一来源（`es/dish-index.json`），不会出现"注解声明的 mapping 和实际 mapping 不一致"这种经典坑。
>
> 另外有个"双召回路"：用户输入的食材**可能不在主数据表里**（比如"松露"），所以除了 `ingredientIds`（keyword 数组）还要查 `ingredientNames`（keyword 数组），两条路都拼进同一个 `should`。

**Q：什么叫"命中"？阈值怎么定的？**

> 命中判定是 `DishSearchService#isDirectEligible()`，是**确定性规则，不是打分阈值**（这点很重要——我没有用一个"相似度 > 0.8 就返回"的拍脑袋阈值）：
>
> 1. **硬门槛**：`missingCount > 0` 直接否。用户手上没有的食材，这道菜就做不了，缺一样都不行；
> 2. **质量门槛**二选一：
>    - 路径 A「充分评价」：`ratingCount >= 10` 且 `ratingWilson >= 0.70`
>    - 路径 B「少量高分」：`ratingCount >= 3` 且 `ratingAvg >= 4.5`
>
> 为什么要有路径 B：一道菜很可能是**刚生成的、还没人评价**，它质量很高（食材全命中）但 ratingCount=0。纯按路径 A 判，新菜永远不能直出，飞轮转不起来。路径 B 让**高质量新菜有机会被直出**。
>
> 这两个阈值是我**调出来的**，不是拍的：早期用的是"10 人 + 威尔逊 0.84"，但我后来算过——**10 次满分（5 分制）算出来的威尔逊下界只有 0.722，根本到不了 0.84**，这个条件永远不可能同时满足，等于直出功能完全失效。所以降到 0.70。
>
> 命中判定通过后，接口返回 `directReturn: true` 这个标记。

**Q：排序怎么做的？为什么 ES 只粗排？**

> 因为**业务指标算不出来**。ES 只能按相关性/字段值排序，但我要的排序依据是"食材满足率、利用率、缺料数"——这些是**集合运算的结果**，需要拿到命中的食材 ID 和用户传的 ID 求交集才知道。
>
> 所以分层是：
> - **ES 粗排**：用 `should` + `term` 快速缩小候选集（假设全库 1000 道，缩到 50 道）；
> - **应用层精排**：把这 50 道的食材全取出来（ES 里已存 `ingredientIds`），在 Java 里算 `missingCount` / `satisfactionRate` / `utilizationRate`，然后**先按缺料上限过滤（strict 要求缺料=0，loose 允许 ≤ 2），再排序**。
>
> **先过滤再排序**这个顺序很重要——如果先排序后过滤，可能排完了才发现全被过滤掉，返回空结果。

**Q：为什么用威尔逊下界不用平均分？（高频）**

> 因为**平均分会被小样本刷分**。一道菜只有 1 个人打了 5 分，平均分 5.0，排名比 200 人平均 4.6 的菜还高——但这个 5.0 毫无统计意义。
>
> 威尔逊下界（Wilson Score Interval Lower Bound）是个**置信下界**：评分人数越多，下界越接近真实平均分；人数越少，下界被压得越低。它天然惩罚小样本。
>
> 公式里 `p = 平均分 / 5`（**归一化到 0~1**）、`z = 1.96`（95% 置信度）。这个口径必须和 ES 索引里存的 `rating_wilson` **完全一致**，否则详情页显示的分数和榜单排序会对不上——这是我踩过的坑。
>
> 公式：`下界 = (p + z²/2n - z·√(p(1-p)/n + z²/4n²)) / (1 + z²/n)`
>
> 补充一句：质量信号不是只用威尔逊，我在发现流里用的是 **`0.65 × 威尔逊 + 0.35 × 互动率`**——因为一道菜"评分高但没人收藏"和"评分高且很多人在收藏"是不同的信号。

**Q：`status` 为什么必须放 `filter` 而不是 `must`？**

> 因为 `filter` 和 `must` 的区别是：**`filter` 不参与打分**。
>
> 如果 `status: 1` 放 `must`，每个候选文档都会+1 分（相当于白给一分），这会让"已发布"的菜在相关性上天然占优，干扰排序结果。放 `filter` 就是纯粹的"必须满足但不加分"，这才是它的语义位置。
>
> **而且这里漏了会出事**：草稿（`status = 0`）是用户生成但**还没发布的私有内容**，如果 ES 查询忘了带 `status` 过滤，**别人能搜到我的草稿**——这是数据泄漏。同理 `deleted` 也必须放 `filter`。

## 四、异步生成与流式输出（简历第 4 条）

> ⚠️ **简历这条要改两处**：① 没有 SSE，实际是轮询；② 没有"从数据库恢复未完成任务"，实际是启动清扫 + 标 `INTERRUPTED`。

### 面试官会怎么问

| 层级 | 问题 | 考察点 |
|---|---|---|
| L1 | 为什么必须异步？同步不行吗？ | 基础判断 |
| L2 | 为什么不直接用 `@Async` 或线程池 submit 就完事？ | 并发模型认知 |
| L3 | **为什么不用 MQ？**（本题最高频） | 队列选型 |
| L4 | 调度线程为什么不能自己执行任务？ | 并发细节 |
| L5 | 队列满了怎么办？用什么策略拒绝？ | 背压设计 |
| L6 | 任务落库了，那状态怎么维护？ | 状态机 |
| L7 | 同一个用户狂点提交怎么办？ | 幂等 / 单飞 |
| L8 | 服务重启了，正在跑的任务怎么办？ | 故障恢复 |
| L9 | 任务会不会重复执行？ | 幂等性 |
| L10 | 超时怎么设？设多少？ | 超时策略 |

### 完整答法

**Q：为什么必须异步？**

> 因为**模型延迟是 12~26 秒**。HTTP 同步等待 26 秒会发生什么：网关/中间件超时、浏览器可能弹超时、Tomcat 线程被长时间占用（高并发下直接打满线程池，整个服务不可用）。
>
> 更关键的：本地 Ollama **并行度是 1**（`OLLAMA_NUM_PARALLEL=1`），意味着后一个任务要等前一个跑完。用户等 26 秒看到结果，如果他还切走做别的、回来发现失败，体验很差。
>
> 所以异步的本质是：**把"等待模型"这件事从用户请求里解耦出去**，用户拿到 taskId 就能走开，回来查状态。

**Q：为什么不用 MQ？（本题最高频）**

> 我确实评估过 RocketMQ / RabbitMQ，选了**自建内存队列 + DB 兜底**，理由有三条：
>
> **① 我需要"改顺序"和"取消排队"，MQ 的语义表达不了。**
> 我这个场景里，用户可能改条件重新提交（新任务应该排前面）或撤销未开始的任务。RocketMQ 的 `consumer` 一旦取到消息就出队了，我要实现"出队前可撤销、可插队"，得自己再造一套状态管理，那还不如一开始就自己写。
>
> **② RocketMQ 的优势在这个规模用不上。**
> MQ 的核心价值是**削峰、跨服务解耦、持久化+重投**。但我是单机部署，峰值并发也就几十，削峰需求有限；而**持久化我本来就用 MySQL 做了**（任务表先落库），MQ 的这个优势被重复建设了。
>
> **③ 引入 MQ 的成本大于收益。**
> 要多一个中间件进程（本身就是故障源）、多一套配置、多一类排查场景。我这个项目更值得投入的是**生成质量**（三道防线）和**内容闭环**。
>
> **代价我也认**：内存队列进程挂了，队列里的任务就丢了——所以我补了启动清扫（下面讲）。如果真要做成生产系统，**MQ 是更稳的选择**，我可能需要的是 `t_ai_generate_task` + 定时扫表补单的组合，而不是纯内存队列。

**Q：调度线程为什么不能自己执行任务？**

> 这是并发编程里的一个经典反模式。因为**一旦调度线程自己去执行任务，它就被占住了**，没人再去从队列里取任务派发给工作线程。
>
> 结果就是：任务 A 正在跑（调度线程被占）→ 队列里堆积了 B、C、D → **没人管它们** → 线程池的其他工作线程全都空转。
>
> 极端情况下会**死锁**：如果任务 A 在执行过程中需要往队列里加任务并等它完成（比如生成过程中又触发生成了下一道），那永远等不到。
>
> 正确做法是严格分离：**调度线程只负责"取任务 + 派发"，工作线程只负责"执行"**。调度线程必须保证**任何时刻都能响应队列的入队事件**，所以它自己不能有耗时操作。

**Q：队列满了怎么办？**

> 我的队列是 `Executors.newFixedThreadPool(2)` + **无界** `LinkedBlockingQueue`，**没有拒绝策略**——因为无界队列在物理上不会满（`offer` 永远返回 true）。
>
> 这看起来是个隐患：理论上内存会被无限占。但我加了一道**前置限流**来替代"队列满拒绝"这个机制：
>
> **`submit()` 里做单用户限流 `maxPerUser = 5`**——同一用户 1 小时内已有 5 个未结束任务，直接拒绝（返回 `EnqueueResult.rejected`），不给排队机会。
>
> 这样做的好处是**拒绝点在入口而不是出口**：用户能立刻收到"提交过于频繁"的明确反馈，而不是排了半天最后失败。反过来，如果用"队列满 + 拒绝策略"，用户要等 20 个任务跑完（几十分钟）才知道自己被拒了。
>
> 事实上因为有这道限流，无界队列在真实使用中不会堆积。

**Q：任务落库了，状态怎么维护？**

> 提交时**先落库再入队**（顺序不能反：先落库拿自增/雪花 ID 作为 taskId）。
>
> 状态机有 6 个值（`AiTaskStatus`）：
> | 值 | 含义 |
> |---|---|
> | 0 | 排队中 |
> | 1 | 生成中 |
> | 2 | 已完成 |
> | 3 | 生成失败 |
> | 4 | 已取消 |
> | 5 | **已中断** |
>
> 任务表还记了 `cost_ms`（模型实际耗时）和 `queue_wait_ms`（排队耗时）——这两个分开记很有用：`cost_ms` 能看出模型健康度，`queue_wait_ms` 能看出并发是否不足。如果只记一个总耗时，你根本不知道慢是因为模型慢还是因为排队。
>
> 另外还有个 `request_signature` 字段，做的是 **MD5 签名的单飞（single-flight）**：同样的请求参数在短时间内重复提交，直接复用已有任务的结果，不重复调模型。这防的是"用户手抖连点 5 次"。

**Q：服务重启了，正在跑的任务怎么办？**

> 我的处理是 **`AiTaskCleanupRunner`（`ApplicationRunner`）在启动时清扫**：把状态是「排队中」或「生成中」、且 `create_time < startupTime` 的任务，全部更新为 **`INTERRUPTED(5)`**，并写 `error_msg = "服务重启导致执行中断，请重新提交"`。
>
> 这里有个细节：判断条件里的 `startupTime` 是一个**实例字段**，在 Runner 构造时记录。为什么要这样？因为 Tomcat 可能在 Runner 执行**之前**就已经开始监听端口了——如果只按"status != 终态"来扫，会把"这次启动后刚提交的、正在正常排队的任务"也误判成中断。这个字段是我调试出来的（见 PITFALLS 里的「启动清扫器的窗口」）。
>
> **为什么不自动重排队？** 两个理由：
> 1. **可能已经写了脏数据**：模型可能已经生成完了一半，草稿可能已经落库了，自动重跑会产生重复数据；
> 2. **用户可能不需要了**：他可能已经等超时自己走了，或者已经重新提交了一个。
>
> 自动重排看起来"更贴心"，但在这两个前提下它是**危险的**。所以我选择**如实告知 + 让用户决定**。
>
> 配套的 `@PreDestroy` 的 `shutdown()` 只清内存队列、**不碰数据库**——因为关机时状态是"任务还没执行"，而这些任务在启动时会被清扫器正确处理。
>
> **如果要做得更完善**，我会加一个 `t_ai_generate_task` 的定时扫表：捞出超时的 `INTERRUPTED` 任务，在用户明确没取消的前提下重新入队，并把"自动重试次数"作为字段记下来，防止无限重试。

**Q：超时怎么设？设多少？**

> `ai.generate.attempt-timeout-seconds = 600`（10 分钟）。这个值是**我踩坑调出来的**，一开始设 240（4 分钟），结果**6 个并发任务全部被判超时失败**。
>
> 根因是：**Ollama 的并行度是 1**（`OLLAMA_NUM_PARALLEL=1`）。6 个任务同时提交，只有一个真正在跑，其余 5 个在 Ollama 内部排队等待。前面那个跑完一个，后面的才开始，单个耗时被放大到远超 4 分钟。
>
> 所以**超时阈值不能凭感觉定**，要结合下游串行资源来算：`最坏情况 = 并发数 × 单次耗时 × 余量`。

**Q：任务会不会重复执行？**

> 同一进程内不会（队列 + 限流 + 单飞签名三重保护）。
>
> 跨重启的情况我**不做自动重放**（上面讲了理由），所以理论上不会重复。但如果未来要做自动重试，必须加幂等键——我现在的 `request_signature` 字段就是为此预留的：重放前先查有没有已完成的同签名任务，有就直接返回它，不重复生成。

## 五、输出保障（简历第 5 条）

> ⚠️ 简历这条要改：没有"降级推荐已有相似菜谱"，实际是**重试 1 次仍失败 → 抛异常 → 任务置 FAILED**。

### 面试官会怎么问

| 层级 | 问题 | 考察点 |
|---|---|---|
| L1 | 小模型输出不稳定怎么保证？ | 核心应对 |
| L2 | 为什么必须 JSON？`format=json` 这个参数模型认吗？ | Prompt 工程 |
| L3 | 除了格式，还要校验什么？ | 校验维度 |
| L4 | 重试时把错误告诉模型，真的有用吗？ | **★ 有没有实测过** |
| L5 | 重试 2 次还是 3 次？依据是什么？ | 参数取舍 |
| L6 | 重试都失败了怎么办？用户看到什么？ | 兜底设计 |
| L7 | Prompt 放在哪？改了要重新打包吗？ | 工程细节 |
| L8 | 怎么知道生成的质量是提升的？ | **★ 评测能力（你的最强项）** |

### 完整答法

**Q：小模型输出不稳定怎么保证？**

> 三道防线，从便宜到贵：
>
> **第一道：让模型只能输出 JSON。**
> 调用时带 `format=json`，Ollama 会强制返回 JSON 结构。这一道挡住的是"带markdown 代码块""带前言后语""用单引号"这类格式污染。
>
> **第二道：后端逐字段校验。**
> `DishDraftValidator#validateDetailed()` 把 JSON 反序列化成对象，然后逐项校验：食材是否都在合法范围、步骤数量是否够、食材克数是否合理、热量是否超范围、必用/禁用食材是否遵守……
>
> 这里我把校验**分成了两档**，分别落库到 `t_ai_generation_record.format_ok` 和 `constraint_ok`。为什么要分开？因为它们代表**完全不同的失败原因**：
> - `format_ok = false` → 模型连结构都没搞对 → **提示词模板可能有问题**，或者该换更大的模型；
> - `format_ok = true` 但 `constraint_ok = false` → 结构对但内容违规 → 是**约束描述不够清晰**。
>
> 不分开的话，你只会看到"失败率 30%"，**根本不知道该去改提示词还是改模型**。
>
> **第三道：带错误信息重试。**
> 把校验失败的具体原因拼回提示词，让模型带着错误信息重新生成。

**Q：重试时把错误告诉模型，真的有用吗？**

> **有用，而且我实测过。**
>
> 实现在 `AiDishGenerator#callModel(userPrompt, previousProblems)`：把校验器产出的每一条 problem 以 `\n- ` 开头追加到 user prompt，标题是「上一次的输出存在下列问题，请全部修正后重新输出」。
>
> 为什么有效？小模型的问题是**"不知道自己错在哪"**，它只能看到自己的输出，看不到失败原因。当你明确告诉它"第 2 步引用了未声明的食材'花椒'"，它下一轮的修正率明显高于让它盲猜。
>
> 效果我在 `es/eval/` 的生成实验里量化过：**首轮通过率和最终通过率的差值，就是重试挽救回来的量**。

**Q：重试 2 次还是 3 次？依据是什么？**

> 代码里 `maxAttempts = 2`——注意措辞，这是**总共 2 次尝试（= 重试 1 次）**，不是"重试 2 次"。我在简历里原来的写法也是"重试 2 次"，这也是个会被抓的表述细节。
>
> **为什么定 2 而不是更多**，三个依据：
> 1. **耗时不允许**。单次生成 12~26 秒，重试 3 次最坏 78 秒。而约束冲突的情况（比如"必用花生"+"禁用花生"）是**不可能成功的**，重试再多也是浪费；
> 2. **自相矛盾的约束要在提交阶段就拒**。我做了前置校验：必用∩禁用、手边食材∩禁用，在提交任务时就抛异常了。否则会让用户白等，实测能跑到 **50~180 秒**才失败；
> 3. **重试预算要留给"可修正"的情况**。格式问题（第 3 道防线能修）值得重试；矛盾约束（重试必然失败）应该在入口拦掉。
>
> 我还有一个隐含的设计：`request_json.constraints` 里的约束**必须进请求签名**。因为约束变了就是另一个任务，如果签名不含约束，就会错误地命中单飞缓存，返回一个按旧约束生成的结果。

**Q：重试都失败了怎么办？**

> **如实置 FAILED，并把失败原因回传给前端。** 这里是 `maxAttempts` 耗尽后抛 `DishGenerationException`，任务状态置 3（生成失败），`error_msg` 写明用的什么食材、约束是什么。
>
> **我没有做"降级推荐已有相似菜谱"**——简历里原来这句话要删掉。原因是：**这个场景下"相似的菜谱"大概率已经有了，如果库里有，前端在调用生成接口之前就已经在检索结果里看到了**（用户是自己点了"让 AI 生成"这个按钮的，说明现有结果他不满意）。再推一遍"相似的"菜谱，是把用户已经拒绝过的内容再喂回去，是负体验。
>
> 如果要在这里做降级，我认为**更有价值的降级方向**是：**给出失败的具体原因 + 可操作的建议**（"你选的食材里没有能搭配的组合，试试去掉 XX"），而不是换一批菜谱。**降级应该降"体验"而不是降"内容质量"**。
>
> 顺带说，项目里有两个容易被误认为"降级"的东西，但都不是：
> - `ReferenceDishRetriever` —— 是**生成前**检索相似菜谱注入提示词做增强（P2-1），让模型写得更贴近库内已有菜谱的风格；
> - `DegradedModeGuard` —— 是**ES 不可用时**按"用户 + 最近 1 小时任务数"限流（默认 5 次），防止 ES 挂了导致所有人疯狂生成、把本地模型打爆。这是**保护系统**，不是保护这次请求。

**Q：提示词放在哪？改了要重新打包吗？**

> 放在 `resources/prompts/dish-generate-system.txt`（73 行），分三块：21~37 行是完整 JSON 骨架、39~66 行是逐字段规则、68~72 行是一个完整示例。
>
> **是的，改了必须重新打包**——它在 jar 里面，`@PostConstruct` 时 `AiDishGenerator#loadSystemPrompt()` 一次性加载成常量。所以改提示词要走完整的 `mvn clean package` + 重启。这是我目前的一个痛点：提示词迭代要和发版绑定，没法热更新。更完善的做法是把它挪到数据库或配置中心，做成可后台编辑的版本管理。
>
> **提示词有版本号**：`AiDishGenerator` 在启动时算提示词内容的 **MD5 前 8 位**作为 `promptVersion`（比如 `1379896b`）。为什么要这个？因为我做过生成质量实验，**如果提示词改了而版本号没变，新旧两组实验数据就混在一起，结论完全无效**。加参考菜谱规则后版本号从 `1379896b` 变成 `076b89e0` —— 这就是在提示我"跨版本比较无效"。

**Q：怎么知道生成质量是提升的？**

> 我建了一套可重跑的实验脚本（`es/eval/`），四支：
> | 脚本 | 测什么 | 指标 |
> |---|---|---|
> | `run-ranking-experiment.py` | 排序策略两臂对照（legacy vs satisfaction） | Precision@5、平均缺料数@5、不足返回率 |
> | `run-generation-experiment.py` | 生成质量（直接生成 vs 参考增强） | 格式/约束通过率、失败率 |
> | `run-load-experiment.py` | 负载（sequential vs concurrent） | 并发下的耗时分布 |
> | `run-synergy-experiment.py` | 检索生成协同 | 直出率能省多少模型调用 |
>
> 前提是 `build-testset.py` 构建**同一份固定测试集**，两臂必须在同一份菜库快照上跑，否则结论没意义。
>
> 我最看重的一个数据是**检索生成协同**：优化排序后直出率提升，意味着**同样流量下模型调用次数下降**——这是省服务器成本的直接体现，也是这个项目"闭环"设计最有说服力的证明。

## 六、额外高频题（简历没写但一定被问）

### Q1：为什么拆成 4 个微服务？规模这么小是不是过度设计？

> **这是个好问题，我的回答是"拆分是为了练手，不是为了架构需要"。**
>
> 真实原因：我这个项目只有 153 道菜、单机能跑，用单体是最合理的工程选择。拆微服务的收益在这个规模**基本不存在**——反而引入了 Nacos、服务发现、网关鉴权、分布式事务这些复杂度。
>
> 但作为个人项目，它的价值在于**完整走一遍微服务链路**：配置中心（多环境配置怎么分层）、注册发现（服务怎么找到彼此）、网关（鉴权、路由、跨域）、以及**服务边界的划分原则**（哪些代码该进 common、依赖方向怎么定）。
>
> 我在这个过程中学到最有价值的其实不是技术栈，而是**约束**：我定了「common 只放跨服务技术能力、领域实体一律不进 common」「依赖方向单向」这两条硬规则。因为不这么约束，common 很快就会变成什么都往里塞的垃圾桶。
>
> 如果重来一次，考虑到规模，我会把 account 和 dish 合一部分，只保留网关和菜品服务。

### Q2：为什么自建父 pom 不继承 `spring-boot-starter-parent`？

> 这确实是我给自己挖的坑，但挖完之后收获很大。
>
> 直接后果是：**自建父 pom 丢掉了 `spring-boot-starter-parent` 默认帮我们配好的两样东西**，我的服务打出的是没有主清单的普通 jar，`java -jar` 直接报错：
> 1. `spring-boot-maven-plugin` 的 `repackage` 目标没有自动绑定 → 补了手写 execution；
> 2. `maven-compiler-plugin` 的 `<parameters>true</parameters>` 没开 → **`@RequestParam` 拿不到参数名，所有需要名字的接口一律 500**。
>
> 第二个坑特别隐蔽：因为 `-parameters` 没开，Spring 拿不到参数名，只能回退用反射猜，而反射拿不到编译期参数名。这个问题的现象是"有的接口 500 有的正常"，非常容易误判成业务 bug。
>
> 所以我现在的口径是：**新项目直接继承 `spring-boot-starter-parent`，这个坑不用再踩第二次。** 但我很感谢它——它让我理解了 Maven 继承体系默认到底帮你做了什么。

### Q3：雪花 ID 为什么转字符串？

> 因为 **JavaScript 的 `Number` 只有 53 位有效精度（`Number.MAX_SAFE_INTEGER` ≈ 9007199254740991）**，而雪花算法生成的是 64 位 Long（19 位数字）。
>
> 后果是：前端 `JSON.parse` 解析大整数时会**静默丢失精度**——`1234567890123456789` 变成 `1234567890123456788`。这个错误不会报错，是**静默的数据损坏**。
>
> 解决方案是全局把 `Long` 序列化成 String。我的做法是在 common 模块里统一配置 Jackson（所有 `Long`/`long` → String），这样**所有服务自动继承**，不会有某个服务漏配。
>
> 前端配套约束：**ID 一律当字符串用，禁止 `Number(id)`**。我还在 PITFALLS 里记了另一个相关的坑——打包时如果嵌进了旧的 common 模块，序列化配置就不生效，同样表现为精度丢失。所以**单独打业务模块必须带 `-am`**。

### Q4：幂等性怎么做的？

> 我在三个层次上做了：
>
> **① 请求级单飞**：同一用户短时间内提交**完全相同**的请求（`request_signature` = 参数 MD5），直接复用已有任务，不重复调模型。防的是手抖连点。
>
> **② 收藏的恢复式设计**：`INSERT ... ON DUPLICATE KEY UPDATE`。这里有个坑——取消收藏是**逻辑删除**（`deleted=1`），但唯一索引**不区分逻辑删除**，所以再次收藏会撞唯一键。解法不是先查后插（会有并发窗口），而是直接 `ON DUPLICATE KEY UPDATE deleted = 0`，**把"取消"和"恢复"当成同一个 upsert 的两个方向**。这也避免了"取消收藏"和"删除收藏记录"被合并成一个操作——那是两个不同的语义。
>
> **③ 任务级不重复执行**：见前面第四节。

### Q5：你这个项目最大的难点/收获是什么？

> **难点是"AI 内容质量不可控"，收获是"把它当成工程问题而不是玄学问题"。**
>
> 一开始我以为生成质量靠调提示词就行，做出来才发现根本不是：格式对但内容违规、热量超标、引用了未声明的食材、禁用花生却用了花生油。
>
> 但当我把它拆成「可测的指标」之后就清晰了：
> - 格式问题 → 能不能被结构化约束住？
> - 约束问题 → 约束描述清不清楚？
> - 质量判断 → **引入外部权威数据**：本地按「成分表(每100g) × 克数 ÷ 人数」算六项营养，**克重覆盖率 ≥ 80% 才采用**（低于这个比例算出来的数没有意义）；本地值可信就标记 `nutrition_source=2`，否则保留 AI 估算。
>
> 这里有个诚实的结论要讲：**本地营养重算实测偏差很大——73 道菜平均绝对偏差 181.79%，最大 825.93%**。原因是调料没有用量数据，导致钠和油脂估算严重偏离。
>
> 这个负结果我保留下来了，因为**它证明我的校验机制是有分辨力的**——它没有"全盘相信 AI"，也没有"全盘替换成自己的计算"，而是按数据可信度分流。这个结论也直接改变了我的设计决策：调料用量必须补进食材主数据。

## 七、临场提醒

1. **主动交代差异，别等被问穿。** 简历上写了没做的东西（IK 分词、SSE），面试官问出来会很难看。**更好的做法是主动改简历**（本文 0.4 给了可直接替换的版本）。
2. **每条答完补一句"这里的坑是"。** 面试官最爱听的是踩坑和取舍，不是流程叙述。
3. **数字要准。** 89 种食材、153 道菜（已发布 112）、161 个 Java 文件、4 个服务。别说"大概一百来条"——说"库里 153 条，已发布 112 条"显得你对项目了然于心。
4. **技术栈必须一致。** 全项目是 **Spring Boot 3.2.4 / Spring Cloud Alibaba 2023.0.1.0 / MyBatis-Plus 3.5.5 / Redisson 3.26.1 / ES 8.16.0 / Ollama(gemma4:e2b) / JDK 17**。别把 Boot 说成 3.5，别提 DeepSeek。
5. **准备好这两个必被追问的深水区**：① 为什么不用 MQ；② 为什么不用 `match` 而是精确匹配。它们是区分"用过"和"想清楚"的分水岭。
6. **承认局限是加分项。** "重启只清扫不重排"、"营养估算偏差大"、"无界队列靠限流兜"——这些主动说出来，比被问出来强一百倍。
