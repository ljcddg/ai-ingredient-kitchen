# AI 灵感厨房 · 面试题预测与答法

> **项目定位**：Spring Cloud 微服务 4 模块 + 本地 LLM 的菜谱生成平台，**内容闭环**是它最大的设计亮点。
> **技术栈**：JDK 17 + Spring Boot 3.2.4 + Spring Cloud 2023.0.1 + Spring Cloud Alibaba 2023.0.1.0 + Nacos + MyBatis-Plus 3.5.5 + Redisson 3.26.1 + ES 8.16.0 + Ollama（gemma3:4b 级）+ Vue3
> **规模**：161 个 Java 文件，4 服务（约 300 种食材 / 100+ 菜谱，库内现149 道）

---

##零、先记住这条主线（答题时反复回扣）

> **这个项目的核心命题是：「AI 生成的内容怎么沉淀成可复用的资产，而不是一次性消耗品？」**
>
> 大多数人做 AI 项目只做到「调通模型」。但这个项目做了完整闭环：
> **用户输入 → 检索菜库 → 命中直出/未命中生成 → 校验发布 → 进 ES 索引 → 被检索/上榜/被收藏 → 反哺直出率**
>
> **没有第 ④⑤ 步（发布 + 进索引），AI 的产出一辈子搜不到，整个功能等于没闭环。**

这一句话就是你和「只会调API 的候选人」的分界线。

## 二、核心技术答法

### A1：项目介绍（60 秒逐字稿）

> 这是一个用 AI 做美食的平台。用户选或输入食材，**系统先在菜库里找现成的——命中高质量的直接返回；没有就让AI 现场生成一道**，生成结果经校验后可以发布进公共菜库，被搜索、被排名、被收藏。
>
> 我认为这个项目最值得讲的不是"用了 AI"，而是**内容闭环**：用户既是消费者也是生产者，AI 生成的内容会沉淀回菜库，**菜库越厚、直出率越高、AI 调用越少**。这个飞轮是整个项目的设计核心。
>
> 技术上��� Spring Cloud 微服务 4 个模块：网关、账号服务、菜品服务，外加一个公共模块。AI 用Ollama 本地部署 gemma3:4b 级别的模型，检索用 Elasticsearch，缓存用 Redis。

**追问：为什么用微服务拆？**
> 按业务边界拆的：`account-service` 管认证、`dish-service` 管菜品和 AI 生成、`gateway` 做统一入口和 JWT 鉴权、`common-service` 放跨服务技术能力。
> **有一条我坚持的约束：依赖方向单向（account/dish/gateway → common），且领域实体一律不进 common。** 否则 common 很快就会变成"什么都往里塞"的垃圾桶，最后谁都不敢改。

### A2：为什么先检索再生成？（★ 核心决策，必答）

**答**（三层理由，从产品到技术）：
> **第一层：省钱省时间。** 本地 5B 级模型生成一道菜要 **12~26 秒**。如果库里已有的菜谱能覆盖用户需求，为什么要重新生成一遍？直出是毫秒级。
>
> **第二层：可靠性。** 库里的菜谱是**已发布、经过校验的**，模型生成的可能是凭空编的。**能复用就不要生成**——这也是为什么我坚持"生成结果必须经过校验才能发布"，而不是生成完就直接进库。
>
> **第三层：飞轮效应。** 直出的前提是库里有货。**如果所有请求都走生成，菜库永远长不起来**；只有生成的内容能沉淀回菜库，才会形成"越用越准"的正循环。所以直出率不只是性能指标，它是**飞轮的输入指标**。
>
> 我的直出规则是**确定性的**：覆盖率 ≥ 0.8 且 评价人数 ≥ 10 且 威尔逊分 ≥ 0.84。**不满足时不返回空**，而是带上可解释的 `missReason`（比如「最接近的『番茄土豆汤』评分偏低（0.70 < 0.84）」），前端据此提示"要不要让 AI 生成一道"。

**追问：直出率现在多少？**
>⚠️ **诚实答**：从检索/生成协同实验看，**严格口径下仍需调模型的比例 93.2%，宽松口径 80.2%**。也就是说直出率目前是 **6.8%~19.8%**，还比较低。
> 为什么低？因为菜库还小（发布状态的 110 道），覆盖不了长尾食材组合。**这也正好说明飞轮还没转起来**——直出率上不去，库就长不起来。
> ⚠️ **注意别吹「直出率 90%」**，你的实验数据不支持。

**追问：怎么提升直出率？**
> 按投入产出排：
> 1. **提发布量**——放宽发布门槛会增加噪音，得不偿失；更好的做法是**手写菜谱**这条线（走同一套校验门槛，但不消耗模型）
> 2. **提菜谱的多样性**——现在的菜「2 人份、不辣」高度集中（112 道里 75 道 2 人份、91 道不辣），维度撑不起来
> 3. **降低门槛的严格程度**——但这会牺牲质量，需要用评测集验证

### A3+A4+A5：延迟处理与自建队列（★ 本项目技术含量最高的一段）

### A3：12~26 秒怎么保证用户体验？

**答**：
> 用户不可能对着转圈等 12~26 秒，所以 `POST /ai/dish` **立即返回 taskId**，前端轮询 `GET /ai/tasks` 拿进度和排队位置。

### A4：为什么不用 MQ？一定要自建队列？

**答**（这是「技术选型取舍」的典型题，务必讲清三个方案的对比）：

| 方案 | 为什么不合适 |
|---|---|
| `ThreadPoolExecutor` + 阻塞队列 | 任务入队后**无法调整顺序**，拿不到稳定的「我排第几」 |
| `PriorityBlockingQueue` | 只在**插入时**排序，插入后**无法重排** —— 与「用户改顺序」直接冲突 |
| MQ（RocketMQ / RabbitMQ） | 「改顺序」「取消排队」在 MQ 模型里很别扭，还要额外维护一份位置状态 |

> 所以我自建了 `DishTaskQueue`：**`lock` 保护的有序 `List`** 做等待队列，**`ConcurrentHashMap`** 记录执行中任务。

**追问：为什么用 `List` 而不是 `PriorityQueue`？加锁不是拖慢性能吗？**
> 答得好，这题是本项目的关键细节：
> **因为业务需要「重排」。** `PriorityQueue` 插入后不能重排，而我的接口要支持用户调整排队顺序（`PUT /ai/dish/ai/tasks/{taskId}/order`，只能在自己任务之间换位）。
> **重排需要整个队列的顺序可见**，无锁队列反而更难写对。
> **而且锁竞争可以忽略**——队列操作频率极低（用户手动换位而已），生成任务要跑十几秒，**读锁的持有时间和写操作频率完全不成比例**。这里用锁是**正确性换性能**，而性能瓶颈根本不在这里。

**追问：你的自建队列是单机内存的，多实例部署怎么办？**
> ⚠️ **这题必须承认局限**：
> 「这是我的取舍：**自建队列是内存级的，单实例下简单可控**。多实例会有两个问题：
> 1. 任务在 A 实例，用户轮询时负载均衡到 B 实例，拿不到状态
> 2. 实例重启任务直接丢
>
> 正确的解法是**把队列状态外置到 Redis**（有序集合 ZSET 存队列，score 是排队序号），调度器从 Redis 抢任务（分布式锁保证只有一个实例执行）。
> 我在README 的决策表里记了这条：**『自建内存队列』放弃的是 MQ 的可靠性和天然分布式能力**。当时选它是因为需求核心是『改顺序』，而这个需求 MQ 表达不了。**如果需求换成『高可靠任务』，我会反过来选 MQ + 状态表。**」

### A5：调度线程为什么不能自己执行任务？

**答**（这题考并发直觉，一定要答）：
> 看这段调度骨架：
> ```java
> while (!interrupted) {
>     synchronized (lock) {
>         while (waiting.isEmpty() || running.size() >= concurrency) lock.wait();
>         next = waiting.remove(0);
>         running.put(next.taskId(), next);
>     }
>     executor.submit(() -> runAndFinish(next));   // ← 交给执行线程池
> }
> ```
> **如果调度线程自己执行任务，它跑一个 12~26 秒的生成时，就没有人去接新任务了**——用户新提交的任务会一直堆在队列里拿不到「排队中」的状态，连队列总览都看不到。
> **调度线程的唯一职责是「调度」**，执行必须扔给独立的执行线程池。这样调度线程永远空闲，随时能响应新任务。

**追问：并发度为什么默认 1？**
> 三个原因：
> 1. **本地单模型串行最稳**——并发调 Ollama 不会让单个请求更快，只是让它们排队，还可能 OOM（显存不够）
> 2. **显存是硬约束**——多个请求同时推理会挤占显存
> 3. **实测不慢**——我做过负载实验，队列不是瓶颈（**排队 ≤239ms**，而生成 P50 是 144.8 秒，排队耗时完全可忽略）
>
> **实测数据支撑决策**：并发组墙钟 391s < 耗时之和 651s（比值 1.66，说明存在重叠）。所以并发是有收益的，但**瓶颈在 GPU 不在队列**，所以我选择「简单串行」而不是「引入并发的复杂度」。

### A6：小模型输出不稳定怎么保证？

**答**（三道防线，每道作用不同）：

| 防线 | 做法 | 作用 |
|---|---|---|
| ① 系统提示词 | 明确 JSON 结构 + 字段规则 + 用量范围 | 告诉它要什么 |
| ② `format: "json"` | Ollama 的**约束解码参数** | 实测有效：不加会裹 ```json 代码块 |
| ③ 应用层校验 + 重试 | 逐字段校验类型/范围，不合格**把具体原因拼回提示词重试 1 次** | 兜住小概率 |

**追问：为什么只重试 1 次？**
> 因为实测小模型的失败模式很集中。我的生成实验统计显示：**格式通过 0.667、约束通过 1.0、一次通过 0.5**。
> **注意这个数据的含义**：约束（字段值范围）从来没失败过，失败的是**格式**（包了代码块导致解析失败）。
> 既然失败主要是格式问题，而 `format=json` 就是治格式的，**加重试的边际收益不高**，所以只重试 1 次。**失败就说人话**：「AI 没能用『X』想出合适的做法，换个搭配再试试」。

**追问：失败信息为什么分两份？**
> **给用户的是人话，给模型的是字段级细节。**
> - 用户：「AI 没能想出合适的做法，换个搭配再试试」
> - 模型：`prepTimeMin=0 不在 2~60 之间`
>
> **把字段级错误展示给用户等于没说**——用户不知道 `prepTimeMin` 是什么，只会觉得"这什么破玩意"。而给模型细节它才可能针对性改对。

**追问：为什么不干脆用更强的模型？**
> ⚠️ 诚实答：
> 「本地部署的核心约束是**显存和数据合规**，所以模型规模受限。而这个场景**对格式和约束的遵循度要求高、对通用推理要求不高**，所以小模型 + 三道防线是合适的性价比方案。
> 如果约束失效（比如必须严格遵循某个复杂格式），我会选择**换模型而不是加更多校验**——因为校验层加到一定复杂度后，维护成本会超过直接换个更听话的模型。」

## 三、ES 检索与排序（★ 第二大技术块）

### A7：`terms` 是 AND 还是 OR？

**答**（这是 90% 的人第一次用 ES 做「包含全部」都会踩的坑）：
> **`terms` 默认是 OR，不是 AND。**
> ```json
> // ❌ 以为这是「必须含 101 和 102 和 103」
> // ✅ 实际语义：含任意一个
> { "terms": { "ingredientIds": [101, 102, 103] } }
> ```
> **正确写法**：每种食材拼一个**独立的 `term` 放进 `must` 数组**，用 `bool.must` 表达「全部满足」。
> 而且这个拼装**只允许在一处做**（`EsDslBuilder.buildIngredientClause`），避免各处写各的、行为不一致。

**追问：`should` 和 `must` 的区别？**
> - `must`：**必须满足**，不满足直接不召回，且**贡献评分**
> - `should`：**应该满足**，不满足也能召回，**但满足会加分**
> - `must_not`：**必须不满足**
>
> 所以「必须包含全部食材」要用 `must`，用 `should` 会导致「只有一种食材的菜」也被召回。

### A8：表外食材（松露）怎么搜到？

**答**（这是本项目一个很关键的设计）：
> 我的食材分两类，走**两条召回路**：

| 食材类型 | 查询字段 |
|---|---|
| 有主数据 ID 的（「番茄」→ id=101） | `ingredientIds`（long 数组） |
| **表外食材**（用户自由输入的「松露」） | `ingredientNames`（keyword 数组） |

> **如果没有第二条路，用了表外食材的菜谁也搜不到。** 这是很容易漏掉的场景——用户自由输入的东西必然没有 ID，而菜谱里确实会用到它。
> 这也解释了我为什么要做「表外食材沉淀」：用户输入的松露先记到 `t_ingredient_candidate`，累计出现 ≥ 3 次才转正成正式食材。

### A14：食材候选为什么「3 次转正」？

**答**：
> 因为**食材主数据是所有归一化和营养计算的基准，一旦被污染，整个召回链路和营养计算都会受影响**。
> 「先计数、够了再转正」是一道缓冲：**让真实需求浮上来，垃圾输入（甚至脏话）自己沉下去。**
> 如果用户第一次输入某个食材就转正，那乱输入会直接污染主数据。

**追问：3 这个数怎么定的？**
> ⚠️ 诚实答：**经验值**。2 太松（一次误输入就污染），5 太严（长尾食材迟迟进不来）。**更好的做法是让它可配置，然后用数据调**——比如观察候选表里不同频次的食材，最终有多少真的变成了高频食材。

### A9：为什么用威尔逊下界不用平均分？（★ 高频）

**答**：
> **因为平均分挡不住刷分。** 一道菜 1 个人打 5 分（平均 5.0），不该压过 100 个人打 4.6 分的菜——**样本量小的评分不可信**。
> 威尔逊区间下界会对样本量做惩罚，**天然抗小样本刷分**。

**公式和原理**：
> ```
> p = 加权平均分 / 5，z = 1.96（95% 置信）
> lower = (p + z²/2n - z·sqrt(p(1-p)/n + z²/4n²)) / (1 + z²/n)
> ```
> **直觉理解**：n 越小，分母里的惩罚项越大，下界被压得越低。所以「1 个人打 5 分」的下界会远低于 1，**而 100 个人打 4.6 分的下界接近 4.6**。

**追问：SQL 侧和 ES 侧的威尔逊口径不一致会怎样？**
> ⚠️ **这是个真实踩过的坑，要认真答**：
> **两边排序会对不上。** 同一个菜，SQL 算出来的分和 ES 算出来的分不一样，会导致「榜单页和搜索页显示的排名不一致」。
> **根因是浮点精度和实现细节**：公式里每一项的运算顺序、精度处理都会造成微小差异，而排序对微小差异很敏感。
> **解法**：两边必须用**完全相同的公式和精度**，最好把公式抽成一处（比如公共方法或常量），而不是各写一遍。

## 四、认证与缓存

### A10：布隆过滤器怎么用的？两条铁律？

**答**（这是全文最值得背的一段）：
> 用户名查重：先问布隆 `mightContain`
> - **false（100% 准确）→ 直接拒绝「用户名已存在」，不查库**
> - **true（可能是误判）→ 查库确认 → 不存在才走 BCrypt → 落库 → 布隆 add**
>
> **两条铁律**：
> 1. 说「**不存在**」100% 可信 → 直接拒
> 2. 说「**存在**」可能是误判 → **必须查库确认**，不能直接拒
>
> **把这两条搞反的后果**：搞反了会把正常用户挡在门外（假阳性），或者放进重复用户名（假阴性）。
>
> **布隆过滤器的性质决定了它只能这么用**：它**只会有假阳性，不会假阴性**——「不在集合里」一定是真的不在；「在集合里」可能是误判。所以它只能用来做「快速排除」，最终判定必须靠数据库。

### A11：Redis 挂了怎么办？

**答**（这部分有两个层次，都要说）：
> **第一层：布隆降级**
> - `mightContain` 失败**一律返回 true** → 退化成直接查库。**宁可慢，不可错**
> - `add` 失败只记 `pendingWrites`，**绝不抛异常**
>
> **⚠️ 这里有个非常容易踩的坑**：注册方法是 `@Transactional` 的，如果布隆 `add` 抛异常，**会把用户已经写好的账号一起回滚掉**！所以**绝对不能抛**。
> 连续失败会进入 **30 秒冷静期**，避免疯狂重试打垮 Redis。
>
> **第二层：全局降级矩阵**（我整个项目的设计原则）

| 依赖 | 挂掉后的表现 | 设计意图 |
|---|---|---|
| Redis | 注册/登录仍可用（布隆降级为直接查库） | **缓存不可用 ≠ 服务不可用** |
| Elasticsearch | 检索返回空列表 → 前端引导走 AI 生成 | **检索是加速器，不是主流程的必要条件** |
| Ollama | 生成任务标记失败，提示重试 | **失败要说人话，不无限重试烧资源** |
| MySQL | **无降级**（唯一强依赖） | source of truth |

> **这张表是我整个项目架构观的浓缩**：我给每个依赖都定义了「挂掉之后的表现」，而不是默认「挂了就没了」。**只有 MySQL 是唯一不能降级的**——它是真源。

## 五、细节题（会被问，考细心程度）

### A12：雪花 ID 为什么转字符串？

**答**：
> 雪花 ID 是 **19 位数字**，超出 JS `Number` 的精度范围（`Number.MAX_SAFE_INTEGER` = 2^53-1，只有 **16 位**）。直接返回前端会**精度丢失**，表现为详情页 404。
> 解法：在 `common` 里用 `JsonAutoConfiguration` 把**所有 `Long` 统一序列化为字符串**，零配置生效。
> 前端因此**一律把 ID 当字符串**，禁止 `Number(id)`。

**追问：为什么在 common 里统一处理，而不是各 Controller 处理？**
> 因为**遗漏是必然的**——只要有一个 DTO 忘了转，那个字段就会出问题。**统一在序列化层处理是唯一可靠的做法**，一处配置覆盖全部场景。

### A13：收藏的唯一键冲突

**答**：
> 取消收藏置 `deleted=1` 后再收藏，`INSERT` 会**撞唯一键**（因为唯一索引不区分逻辑删除）。
> 正确做法是**恢复式收藏**：
> ```sql
> INSERT INTO t_dish_collect (dish_id, user_id, deleted) VALUES (?, ?, 0)
> ON DUPLICATE KEY UPDATE deleted = 0, create_time = NOW();
> ```
> **另外一条铁律：计数一律按明细表重算，绝不用 affected rows 做加减。** 因为 `ON DUPLICATE KEY UPDATE` 的 affected rows 语义很怪（0、1、2 都可能），用它算计数一定会错。

### A16：索引和数据库不一致怎么办？

**答**：
> 我有专门的 `t_es_sync_task` 表做**索引同步待办**，支持：
> - **退避重试**——失败的任务按指数退避重试（10s × 2^retry，最大 5 次，上限 300s）
> - **人工补偿入口**——管理接口可以手动重试失败任务，不用等下一次退避
> - **积压统计**——`/ai/es/sync/status` 能看待同步/完成/待重试/待放弃各多少，**这是排查「为什么索引里没有这道菜」的关键入口**

**追问：为什么用「最终一致」而不是强一致？**
> 「索引是**查询加速器**，不是真源；真源是 MySQL。所以索引可以滞后，但**不能永久滞后**——所以必须有退避重试 + 人工补偿双保险。
> **强一致的代价太高**：为了一个查询加速器去保证强一致，收益和成本完全不匹配。」

### A17：执行中取消怎么做的？

**答**（要诚实，这是明确记为优化项的）：
> ⚠️ **目前只做了逻辑取消**——把任务标记为 `CANCELLED`，但不会真正中断正在跑的推理。
> 原因是：**要真正释放资源需要流式 + 断连改造，收益不抵复杂度**。
> 如果要做，思路是：生成时用 `Stream<String>` 接收输出，**定期检查取消标记**，发现已取消就丢弃后续输出。
> 这条我在决策表里明确记成了**优化项**而不是藏着——因为它是我主动判断「暂时不值得做」的。

### A18：重启后任务怎么办？

**答**：
> 我标记为 **`INTERRUPTED`**，**不自动重新入队**。
> 理由是：**重放会产生重复草稿**（同一个任务生成两次会留下两道重复的菜）。所以**让用户自己决定更安全**——看到"上次生成中断了"，可以选择重新生成或者放弃。
> **这也是「至少一次投递 + 幂等」的另一种体现**：不盲目重试，避免副作用。
