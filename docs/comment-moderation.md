# 评论违规词拦截与举报审核 · 设计说明

> 对应代码：`dish-service/.../moderation/`、`service/SensitiveWordService`、
> `service/CommentModerationService`、`controller/CommentModerationController`、
> `frontend-vue/src/views/AdminView.vue`（违规词库 / 举报审核两个 tab）
>
> 建表：`sql/migration-09-comment-moderation.sql`
> 词库导入：`sql/import-sensitive-lexicon.py`

## 1. 要解决什么

评论是全站唯一「用户自由输入 + 立即展示给所有人」的入口。这一层如果不做，会出现两类问题：

1. **广告与辱骂刷屏**。一条「加微信 xxx 领资料」在热门菜下面挂一天，比任何功能缺陷都伤产品。
2. **违法内容无兜底**。涉枪涉爆、赌博博彩这类内容一旦出现，平台是要担责的。

但也不能走向另一个极端：一发现敏感词就整条拒绝。用户写了 200 字做菜经验，
因为其中一个词被整体丢弃，体验比「那个词变成星号」差得多，而且他不知道为什么被拒。

所以设计目标是三个：

- **拦得住**：常见变体（插空格、插符号）也要命中
- **不误伤生产**：正常评论不该被整条干掉
- **留痕可追溯**：为什么屏蔽、谁处理的、依据是什么，事后都查得到

## 2. 数据模型

### 2.1 `t_sensitive_word`（违规词库）

| 字段 | 类型 | 说明 |
|---|---|---|
| `word` | VARCHAR(255) | 违规词。入库前统一去干扰符 + 英文小写 |
| `category` | VARCHAR(16) | `AD` 广告导流 / `PORN` 色情低俗 / `VIOLENCE` 暴恐 / `ILLEGAL` 违法违规 / `ABUSE` 辱骂攻击 / `OTHER` |
| `level` | TINYINT | **1 = 替换为星号**（评论照常发）；**2 = 整条拦截待审**（不进详情页） |
| `enabled` | TINYINT | 0 停用 / 1 启用 |
| `source` | VARCHAR(64) | `manual` 人工录入，`lexicon:<文件名>` 批量导入 |
| `hit_count` | INT | 累计命中次数，管理页按它排序能看出哪些词最常被触发 |

三个设计决定：

- **`category` 用字符串不用数字**。类别会被运营扩展（今天 5 类，明年可能 8 类），
  数字枚举每加一类都要改前端映射、改注释，还要记住「4 到底是色情还是违法」。
- **不加 `UNIQUE KEY(word)`**。本表用逻辑删除，MySQL 唯一索引会把已删除的行也算进去 ——
  删掉「加微信」之后想加回来会撞唯一键。查重放 Service 层（只查 `deleted = 0`），
  和 `t_dish_collect` 踩过的坑是同一类。
- **`source` 是给运维用的**。批量导入必然混进误伤词，出问题时得能「按来源整批停用」，
  否则只能在列表里一条条点，而一条条点一定会漏。

### 2.2 `t_comment_report`（举报）

| 字段 | 说明 |
|---|---|
| `comment_id` / `dish_id` | 被举报评论 / 其所属菜品（`dish_id` 冗余，审核列表要显示「哪道菜」） |
| `reporter_id` | 举报人 |
| `reason_type` | 0 其他 / 1 广告导流 / 2 辱骂攻击 / 3 色情低俗 / 4 违法违规 |
| `status` | 0 待处理 / 1 已受理（评论已下架）/ 2 已驳回 |
| `handler_id` / `handle_remark` / `handle_time` | 处理人、说明、时间 |

`reason_type` 用枚举而不是自由文本：审核页要按理由聚合（「这个月广告举报占多少」），
自由文本聚不出来。自由文本只做补充（`reason`，可空）。

### 2.3 `t_dish_comment` 扩列

| 字段 | 说明 |
|---|---|
| `hit_words` | 命中的词，逗号分隔。**只有管理员看得到** |
| `report_count` | 被举报次数，达 3 次自动转待审 |
| `audit_remark` | 管理员处置说明（下架/放行的依据） |

原有 `status` 直接复用：0 待审核 / 1 正常 / 2 已隐藏。没有为治理功能新建评论表 ——
评论只有一张，状态机也只该有一套。

## 3. 匹配算法：字典树 + 最长匹配

### 3.1 为什么不用 `String.contains`

词库 N 条、评论长度 L，逐个 `contains` 是 O(N·L)。词库涨到 1.5 万条时，
一条 500 字评论要做几百万次字符比较，而且**每来一条评论都得重来一遍**。

字典树把词库压成一棵字符树，扫描时从每个起点沿树往下走，一次遍历找出所有命中，
复杂度降到 **O(L × 最大词长)**，与词库大小基本无关。

实测（15668 条启用词，含 1.5 万条域名）：

| 指标 | 数值 |
|---|---|
| 构建耗时 | **38 ms** |
| 内存增量 | **+15 MB** |
| 单条评论扫描 | **5–44 μs**（首次含 JIT 预热约 1 ms） |

### 3.2 三个必须做对的点

**① 最长匹配优先。** 词库同时有「加微」和「加微信」时，命中的必须是长的那个。
否则短词先命中，会把长词切成两半，替换后残留可读的半截内容。
实现上是沿树一直走到底，记录最深处的完整词。

**② 命中区间不重叠。** 替换过的区间直接跳过（`i = matchedEnd + 1`），
避免同一位置被反复覆盖。

**③ 插字符绕过。** 「加 微 信」「加\*微\*信」是最常见的规避手法。
做法是：扫描前先把空白和常见分隔符抽掉，同时记录「有效字符 → 原始下标」的映射；
命中后按原始下标回填星号，被跳过的空格和符号一起盖掉。

```
原文   请 加 微 信 详聊
有效   请 加 微 信 详聊      ← 抽掉空格，记录原下标 [0,1,3,5,7,8]
匹配        └─加微 信─┘      ← 在有效序列上命中
回填   请 *  *  *  *  详聊   ← 按原下标 1..5 覆盖，空格一起变成星号
```

词尾的空格属于正常分隔符，保留 —— 吃掉它会把句子粘起来（`***详聊`）。

### 3.3 线程安全：整体替换，读路径无锁

词库是启动时载入、管理端偶尔变更。**重建时不是往旧树里加词，而是构建一棵新树再替换引用**
（`volatile`）。原因：字典树在使用中被修改，正在扫描的线程会看到半成品结构
（某个词的前缀挂上去了、但它自己还没标记为完整词），结果是「刚才还能拦住的词突然拦不住了」。
整体替换让读线程要么看到旧树、要么看到新树，不存在中间态。

重建本身用 `synchronized` 串行化，避免两个管理员同时改词互相覆盖。评论发布路径**完全无锁**。

### 3.4 降级

词库表不存在、或读取失败时，保留上一版（或空树），**评论功能照常可用**（只是不拦截）。
拦截是保护措施，保护措施自己挂了不该把被保护的东西一起拖下水。

## 4. 处置分流

| 命中级别 | 处置 | 用户侧表现 | 为什么 |
|---|---|---|---|
| level 1（广告、辱骂） | 命中的词替换成等长星号，评论正常发布 | 看到 `想学的***联系我`，并有「部分内容已屏蔽」提示 | 整条丢弃对用户损失太大 |
| level 2（色情、涉枪涉爆、违法网址） | 落库但 `status = 0`，不进详情页 | 提示「已提交，管理员审核通过后展示」 | 违法内容不该只变成星号后继续展示 |

**存库的是脱敏后的文本，不是原文。** 详情页查询只按 `status = 1` 取，
若存原文，替换就白做了。命中词单独记在 `hit_words` 里，管理员据此解释「为什么被屏蔽」；
至于被盖掉的那几个字，管理员不需要看 —— 上下文完整就够了。

## 5. 举报与审核

### 5.1 状态机

```
评论 status:  0 待审核 ──approve──> 1 正常 ──(举报≥3 次)──> 0 待审核
                    │                 │
                    └───hide──────────┴──> 2 已隐藏 ──(管理员可再放行)──> 1

举报 status:  0 待处理 ──handle(remove)──> 1 已受理（评论被下架）
                    └────handle(reject)──> 2 已驳回
```

### 5.2 三条硬规则

**① 举报不能让内容消失。** 举报只做两件事：把争议内容推进待审队列（从公开列表摘掉）、
给管理员一个排序依据。是否恢复展示、是否彻底隐藏，必须由人决定并留痕。
否则任意 3 个账号约好就能让别人的内容消失，攻击成本为零。

**② 一人一条一次。** 同一个人对同一条评论只能有一次待处理举报（Service 层查重）。
不靠唯一键：`(comment_id, reporter_id)` 的唯一索引会和逻辑删除打架，
而且「举报过还能不能再举报」本身是业务规则，写进索引就改不动了。

**③ 下架不删行。** 评论置 `status = 2` + 写 `audit_remark`。删掉之后「当初为什么下架」
只能靠记忆，用户申诉时也无从核对。

### 5.3 处理举报时的连带动作

- `remove`（受理）：评论下架，**同一条评论的其他待处理举报一并关闭**（标记已受理）。
  否则管理员会把已下架的评论再「下架」一次，列表也清不干净。
- `reject`（驳回）：只关这一条，评论保持原样。
- `approve`（待审评论放行）：连带把还在待处理的举报**驳回** —— 内容是管理员看过的，
  举报不再成立。

## 6. 词库运营

### 6.1 为什么不能整包导入开源词库

本次接入的是 [Sensitive-lexicon](https://github.com/Konsheng/Sensitive-lexicon)（MIT）。
它的词表按主题分文件，但**混入了大量正常词**：

| 文件 | 混入的正常词 | 后果 |
|---|---|---|
| 广告类型.txt | 网络、招聘、淘宝、兼职 | 正常讨论「招聘」被刷成星号 |
| 色情词库.txt | 刺激、写真 | 「火候刺激」被刷成星号 |
| 民生词库.txt | 打人、拆迁 | 新闻式讨论被误伤 |

所以导入必须过三道闸：

1. **停用词**：业务上确定不能拦的通用词（见脚本 `STOPWORDS`）
2. **长度闸**：1 字词误伤率极高；超长词多半是拼出来的垃圾域名
3. **纯 ASCII 短词闸**：`LY`、`3J` 这类缩写几乎全是误伤

另外，词库里的**政治/时政类文件不在本模块处理范围**，脚本既不读取也不输出其内容 ——
一个美食社区的评论治理用不上它们，且这类词条的误伤率与合规风险都远高于收益。

### 6.2 本次导入结果

| 类别 | 文件 | level | 导入条数 |
|---|---|---|---|
| 广告导流 | 广告类型.txt | 1 | 104（另过滤停用词 10、缩写 6） |
| 色情低俗 | 色情类型.txt + 色情词库.txt | 2 | 536（去重后） |
| 涉枪涉爆 | 涉枪涉爆.txt | 2 | 431 |
| 非法网址 | 非法网址.txt | 2 | 14581（过滤超长 6） |
| 人工种子 | —（建表脚本内置） | 1/2 | 16 |
| **合计** | | | **15668** |

导入是幂等的（`INSERT ... SELECT ... WHERE NOT EXISTS`），重复执行不会插重复行；
每约 400 条一批，生成的 SQL 约 3.3 MB。

### 6.3 日常维护

管理页 `/admin → 违规词库` 提供：

- **检索**：关键词 + 类别 + 级别 + 启用状态，四个条件组合
- **增删改 / 启停**：改完自动重建内存词库，下一次评论立刻生效
- **文本试跑**：输入一段话，直接看到「替换后是什么样、命中了哪些词、会不会整条拦截」。
  这是最实用的一个 —— 新加一个词能不能用、会不会误伤，跑一遍比盯着词表猜靠谱。
  它读的是**同一棵内存树**，所以结果和用户实际看到的完全一致。
- **按来源停用**：整批导入出现问题时的收口手段

## 8. 已知限制

1. **误伤仍需人工复核**。15668 条里 1.45 万条是历史垃圾域名，命中率低但内存占用最大；
   若发现某批词误伤，用「按来源停用」整批收掉，不要一条条删。
2. **不做拼音 / 谐音 / 拆字变体**。「加威信」「+V」这类变体匹配不到。
   要做需要引入拼音转换或编辑距离（词库规模下开销不小），当前判断收益不抵复杂度。
3. **举报不防刷**。同人同评论只能举报一次，但换账号仍可刷。
   真要防需要全局写接口限流，不该在这一处堆特例。
4. **词库不跨服务共享**。目前只有 dish-service 用；若 account-service 也需要
   （比如昵称过滤），应把词库与匹配器下沉到 `common`，而不是两边各存一份。
