## 二、任务队列（这套需求里技术含量最高的部分）

### 2.1 先排除三个"看起来能用"的方案

| 方案 | 为什么不行 |
|---|---|
| `ThreadPoolExecutor` + 阻塞队列 | 任务一旦入队**无法调整顺序**，`BlockingQueue` 只有 FIFO/优先级，没有"重排"语义；而且 `execute()` 会立刻提交，队列只在忙时缓冲，拿不到稳定的"排队位置" |
| `PriorityBlockingQueue` | 只在**插入时**按优先级排序，插入后**无法重新排序** —— 与"用户改顺序"直接冲突 |
| 上 MQ（RocketMQ / RabbitMQ） | 消息躺在 broker 里，**用户改顺序、取消排队**这两件事在 MQ 模型里非常别扭；而且要知道"我排第几"还得额外维护一份状态。多一个组件换不到任何收益 |

**结论：自建一个内存调度器**（单实例）。等将来真要多实例了，再换 Redis ZSet 做分布式队列，语义可以完全对齐。

### 2.2 调度模型

```
提交 ──► waiting（有序列表，可任意重排）
              │
              │  调度线程：waiting 非空 && running < 并发度
              ▼
          取列表第一个 ──► running（执行中，最多 N 个）
              │
              ▼
        执行线程调 Ollama ──► 成功/失败 ──► 落库 + 出队
```

核心数据结构：

```java
// 等待中的任务：用有序 List，因为要支持"重排"
private final List<TaskHandle> waiting = new ArrayList<>();
// 执行中的任务：按并发度上限控制
private final Map<String, TaskHandle> running = new ConcurrentHashMap<>();
private final int concurrency;   // 默认 1，见 2.5
private final Object lock = new Object();
```

**关键点：不要用 `ConcurrentLinkedQueue` 之类的无锁队列** —— 重排操作需要整体可见的顺序，用一个 `lock` 保护 `waiting` 反而最简单也最不容易错（队列操作的频率极低，锁竞争可以忽略）。

调度线程的骨架：

```java
while (!Thread.currentThread().isInterrupted()) {
    TaskHandle next;
    synchronized (lock) {
        while (waiting.isEmpty() || running.size() >= concurrency) {
            lock.wait();               // 没活干就睡，有提交/有完成时唤醒
        }
        next = waiting.remove(0);
        running.put(next.taskId(), next);
    }
    executor.submit(() -> runAndFinish(next));   // 交给执行线程池，别阻塞调度线程
}
```

> **别让调度线程自己执行任务** —— 否则它在跑一个 10 秒的生成时，没人能接新任务，
> 用户提交后连"排队中"的状态都拿不到。

### 2.3 任务状态机

```
              submit
                │
                ▼
   ┌──────── PENDING ────────┐
   │  （排队中，位置可见）      │
   │         │               │
   │   cancel│       调度取出  │cancel
   │         ▼               ▼
   │     CANCELLED        RUNNING ────► SUCCESS
   │                    （生成中）  └──► FAILED
   │                         │
   └─────────────────────────┘
        cancel（执行中）= 置取消标记 + Future.cancel(true)
```

**两条规则必须写死在服务层**：

1. `SUCCESS` / `FAILED` / `CANCELLED` 都是**终态**，不能再流转
2. 只有 `PENDING` 和 `RUNNING` 的任务可以被取消

**改进阶段补的实现（P0-3）**：上面这两条原先只是"检查后再更新"，
**检查与更新之间有竞争窗口** —— 两个线程可能都读到 `RUNNING`，然后都去写结果，
失败分支还可能覆盖掉用户刚点的取消。现在改成**条件更新抢状态迁移权**：

```java
// 只有把 status 从 from 改成 to 的那一次更新才算"占有"了这次迁移
taskMapper.update(entity, lambdaUpdate().eq(id).eq(status, from));
```

`DishTaskStateMachine` 定义合法迁移，`DishTaskCompletionService` 负责"只有抢到完成权的任务才能发布结果"，
失败分支同样走条件更新、**不允许覆盖已取消状态**。
结果唯一性由 `t_ai_generation_record` 的 `UNIQUE KEY uk_task(task_id)` 兜底：
即使重复执行，也只会有一条生成记录（详见 [`database.md`](database.md) 第十节）。

### 2.4 四个操作的语义（这里有坑）

| 操作 | 排队中（PENDING） | 执行中（RUNNING） |
|---|---|---|
| **取消** | 从 `waiting` 移除 + 置 `CANCELLED`。**真正省资源** | `Future.cancel(true)` + 置取消标记。**注意：底层 HTTP 请求未必真的断掉**（见下方说明） |
| **调整顺序** | 改 `waiting` 里的下标，立即生效 | 不允许（已经在跑了） |
| **查询位置** | 返回 `waiting.indexOf(task) + 1` | 返回 0（正在做） |
| **重复提交** | 单飞去重：同 `signature` 直接返回已有 taskId | 同左 |

**关于"取消执行中的任务"必须说清楚**：`Future.cancel(true)` 只是给线程打中断标志。
Ollama 的 HTTP 调用是阻塞 IO，**中断不一定能让请求停下来** —— 请求可能仍在服务端跑完。
所以：
- **排队中取消 = 真省资源**（根本没开始）
- **执行中取消 = 逻辑取消**（不入库、前端立即看到取消），资源可能仍被占用一小会儿

要真正做到"执行中也能省资源"，得改用**流式调用**（`stream=true`）+ 在回调里检查中断标志，
提前关闭连接。这是个明确的优化项，**建议第一版不做**，先把队列跑通。

**改进阶段的两条实测补充（P1-3 / P1-6）**：

1. **取消要如实回答**。以前无论成没成，前端都收到一句"已取消"。
   现在 `DishGenerateService.cancel()` 会检查实际状态，答不出效果就直说：
   「任务已成功，取消没有生效」。
2. **逻辑取消不释放模型槽位**。实测：上一个任务被取消后，下层推理继续跑完，
   新任务在应用队列里干等，`queue_wait_ms = 240142`（约 4 分钟），
   而那一次的 AI 耗时本身只有 169 秒。压测和演示都要把这一条算进去。

### 2.5 并发度

| 设置 | 说明 |
|---|---|
| `concurrency = 1`（**默认**） | 本地 5.1B 模型串行执行。实测热态 3~4 秒/次，串行完全够用，且不会互相拖慢 |
| `concurrency = 2` | 只有在有独立 GPU、且测出并发不掉速时才开 |

**并发度必须是配置项**（`ai.queue.concurrency`），不能写死 —— 换机器、换模型都要调。

**改进阶段的实测结论（重要）**：应用侧并发 2、而 Ollama `OLLAMA_NUM_PARALLEL = 1` 时，
两个请求会落到同一个模型实例上分时复用 —— 负载实验里一次 2 vs 4 的对照
**6/6 任务全部失败**，`error_msg` 一律「模型响应超时（超过 240 秒）」（阈值当时定的 240s，
把"并发下变慢"误判成了"卡死"；现阈值已提到 600s）。
实测把 Ollama 并行度提到 2 需要先把上下文从 40960 调小（KV cache ≈ 上下文 × 并行数，
8G 显存放不下 40960×2，会回退 CPU，单请求 2.5s → 7.4s），
**用户已决定维持并行 1**；应用侧队列不是瓶颈（实测排队 ≤ 239ms），瓶颈是单次模型调用。

### 2.6 单用户排队上限

不限的话，用户连点就能塞几十个任务，把队列排到天荒地老。

`ai.queue.max-per-user = 5`（可配置），超了直接拒绝并提示"你已有 N 个任务在排队"。

### 2.7 服务重启怎么处理

内存队列一重启就没了，但 DB 里还留着 `PENDING` / `RUNNING` 的记录 ——
**如果不处理，这些任务会永远卡在"生成中"，前端一直转圈。**

启动时做一次清扫（`ApplicationRunner`）：

```sql
-- 把上次没跑完的任务标记出来，让前端能显示"已中断，请重试"
UPDATE t_ai_generate_task
SET status = 'INTERRUPTED', finish_time = NOW()
WHERE status IN ('PENDING', 'RUNNING');
```

**为什么不做"自动重新入队"**：任务可能已经写了一部分草稿进库，重新跑会产生重复数据；
而且用户可能早就不需要了。**让用户自己决定要不要重试**，比自动重放安全。

**改进阶段的实现与验证（P0-3）**：清扫走的也是条件更新（只动 `PENDING` / `RUNNING`），
落成 `status = 5` + `error_msg =「服务重启导致执行中断，请重新提交」`；
端到端验证跑过"重启后卡住的任务被如实标成中断"这条路径，
另外两件事一起补齐了：

- **结果唯一关联**：`t_ai_generation_record` 上 `uk_task`，重复执行不会写两条记录；
- **恢复测试**：重启清扫 + 用户重试构成一条完整链路，不是"只写了 SQL 就算做了"。

### 2.8 接口清单

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/ai/dish` | 提交生成请求 → 立刻返回 `taskId` + 排队位置 |
| `GET` | `/ai/tasks` | 我的任务列表（含状态、位置、进度） |
| `GET` | `/ai/tasks/{taskId}` | 单个任务状态（轮询用） |
| `PUT` | `/ai/tasks/{taskId}/order` | 调整排队顺序，body: `{"targetIndex": 2}` |
| `DELETE` | `/ai/tasks/{taskId}` | 取消（排队中 / 执行中都走这个） |
| `GET` | `/ai/dish/{dishId}` | 菜品详情（营养 / 步骤 / 大厨建议 / 评论 / 评分） |

**前端交互建议**：提交后不要阻塞，把任务卡片插到列表里，然后每 1.5 秒轮询 `/ai/tasks`。
队列位置变化要能实时反映在 UI 上（这是"排队"体验的关键）。
SSE 更好但复杂度高，**第一版用轮询足够**。

### 2.9 多用户公平性（必须现在就定规则）

这是我在你的需求里看到的最容易出问题的一点：

> "等待队列可以修改顺序"

如果队列是**全局**的（所有用户共用一个 Ollama），那"用户能改顺序"就有了歧义 ——
**A 凭什么把自己的任务插到 B 前面？**

**建议规则（也是我要跟你确认的点）**：

1. 队列是**全局**的（因为本地 Ollama 是独占资源）
2. 用户**只能在自己提交的任务之间调整相对顺序**
3. 用户**不能**跨越别人的任务移动位置
4. 实现上就是：`move` 操作只在"属于当前用户的任务所占的下标集合"里做交换

这样既满足"我能调整自己的几个请求先后"，又不会变成互相插队的抢椅子游戏。

## 三、食材自由输入

### 3.1 归一链路

前端不仅要能多选，还要能输入任意食材名。后端的处理顺序：

| 步骤 | 做法 | 命中率 |
|---|---|---|
| 1. 精确匹配 | 查 `t_ingredient.name` | 高（列表内的） |
| 2. 别名匹配 | 查 `t_ingredient.alias`（逗号分隔的多别名，最多 4 个："西红柿,tomato"；89 种食材里 88 种有别名） | 较高 |
| 3. 模糊/向量兜底 | 用 AI 或字符串相似度归一 | 剩下的一小撮 |
| 4. 仍然匹配不到 | **记进候选表 `t_ingredient_candidate`（计数 + 待审）**，本次生成照常进行，食材按名字落库 | —— |

第 4 步不直接写正式主数据，理由和菜品一样：**UGC 不能直接进公共池**，
否则用户乱输的"阿巴阿巴"会污染食材主数据，进而污染召回与营养基准。
次数只用来排待办顺序，**转正必须由管理员逐条判定**（`/ai/ingredients/candidates/approve|reject`，驳回必填理由）。

**落库时还会再归一一次（这条以前漏了）**：生成结果进入 `DishDraftWriter.save()` 时，
食材 ID 先按"用户勾选的列表"取；取不到就回退 `IngredientDirectory.resolveId()` ——
也就是说 AI 自己补进来的食材、用户在输入框自由敲的食材，只要主数据里认得出（正式名/别名/去空白与大小写），
一样能拿到 `ingredient_id`，从而**进得了按 ID 的精确召回、算得了营养**。
真的认不出才按表外处理（`ingredient_id = NULL` + 记候选表）。
历史遗留的空值由 `sql/migration-05-ingredient-id-backfill.sql` 补（只补"唯一能对上"的：
正式名相同，或别名命中且该别名只属于一条主数据；开发库实测 6 行 → 0 行）。

**加载顺序是有讲究的**：`IngredientDirectory.refresh()` 分两遍登记 ——
第一遍只登记正式名，第二遍才登记别名。因为数据里存在真冲突（「五花肉」既是自己的正式名、
又是「猪肉」的别名），一遍登记的结果取决于数据库返回行的顺序，同一个名字今天归到甲、明天归到乙，
缺料判断和营养计算跟着一起抖。现在**正式名优先、别名让位**，冲突会打 warn：

```
食材目录已加载：89 种食材（其中常备调料 16 种），280 个可归一化名称；
有 1 处名字冲突（已按「正式名优先、别名让位」处理，建议整理 t_ingredient.alias）：[「五花肉」→ 保留 143，忽略 109]
```

### 3.2 营养策略（改进后已翻案：本地按成分表计算为主，AI 估算降级并标注来源）

**原方案**是"营养值统一由 AI 输出，前端标注「AI 估算，仅供参考」"，理由是食材能自由输入、
主数据覆盖不全。**改进阶段把它翻了过来**，因为实测偏差不支持"以 AI 为准"：

> 同一批菜，AI 估算与本地计算的**平均偏差 181.79%、最大 825.93%**
> （端到端脚本 `dish-service/verify-p2-nutrition.py` 的 Report，71/73 道菜从 AI 值切成
> 本地值，脚本用独立实现的算式复算，六项营养全部与库内一致）。

而 `t_ingredient` 本来就带每 100g 的 calorie / protein / fat / carb / fiber / sodium 与 `unit_gram`
（89 种里 87 种有值）—— 数据底子在，只是一直没被当成"用户可见的营养值"。

**实现**：`ai/NutritionCalculator.calculate(List<Item(name, grams)>, servings)`
按「每 100 克成分 × 克数 ÷ 人数」算；名字先经 `IngredientDirectory.resolveId` 归一（与召回同口径）。
`trustable()` = `coverage >= MIN_COVERAGE(0.8)` 且 `resolvedItems > 0`；
查成分表失败时返回"不可信结果"，**不硬算**。

| 情况 | 营养值 | `nutrition_source` | `nutrition_verified` |
|---|---|---|---|
| 覆盖度 ≥ 0.8 且至少命中 1 个食材 | 本地计算 | 2 本地计算 | 1 |
| 覆盖不足（自由输入 / 食材缺成分值） | 保留 AI 值 | 1 AI 估算 | 取生成时的核对结果 |

**口径边界必须一起说**：调料没有用量，所以本地计算**不含调料热量**，会系统性偏低 ——
它是"有据可依的估算"，不是实测营养值。

**前端标注**：列表卡片与详情页**必须同口径**。详情页曾经用 `!verified` 反推"是不是 AI 估的"，
把"本地算但未核对"的菜标成了 AI 估算，而列表按 `nutritionSource` 渲染 —— 同一道菜两处说法不同
（后端 `DishDetailView.NutritionView` 因此补了 `nutritionSource` 字段，前端按三档渲染：
AI 估算 / 本地计算未核对 / 本地计算已核对）。

**整库重算**：`POST /ai/admin/nutrition/recompute`（需管理员）返回
`scanned / updated / skipped / meanDeviationPct / maxDeviationPct / localSourceTotal / queuedSync`，
每更新一道菜就登记一次 ES 同步（复用第四节的待办表）。

### 3.3 手写菜谱：用户自己写的那条路（不走模型）

AI 生成之外，用户也可以**自己写一道**（`t_dish.source = 3`）。前端入口是食材页的
「手写菜谱」按钮 —— **就地展开面板，不跳页**：用户手上刚选好的食材和人数不该因为跳走而丢掉，
面板默认就用它们预填。

| 环节 | 做法 | 为什么这么做 |
|---|---|---|
| 试算 | `POST /api/dish/ai/dish/manual/preview` 只算不写库：按成分表算营养，并把"还差什么"列出来（返回 `problems` / `warnings` / `ready`） | 发布门槛（≥2 样食材 / ≥3 条步骤 / 菜名 ≤20 字 / 热量 > 0 / 不与已发布菜重名）必须让用户**上传前**就看到。只在提交后告诉他，等于让人白填一遍 |
| 落库 | `POST /api/dish/ai/dish/manual` **一律先存草稿**（`status=0`），再调 `DishPublishService.tryAutoPublish(dishId)` | 与 AI 那条路完全对称：草稿先落库，发布是另一件事。校验不过只留在草稿，**绝不**因为够不到发布门槛就把用户写的内容整体回滚 |
| 营养 | 复用 `NutritionCalculator`：覆盖率 ≥ 0.8 且至少命中 1 样 → 写本地六项 + `nutrition_source=2` + `verified=1`；否则标注为估算 | 两条路一个口径，详情页/列表的标注才不需要为"这道菜是谁写的"分叉 |
| 食材 | 名字先走 `IngredientDirectory.resolveId()`，真的表外才记候选表 | 与 AI 生成同一条归一链路，手写不会绕开主数据 |
| 命名 | `nameKey = normalizeName(name)`，与**已发布**菜比对（`(name_key, creator_id)` 唯一） | 重名检测在库层面统一：手写菜撞了 AI 菜的名字，一样发不出去（这条只能查库，面板提前提示不了） |

**成分表里的空行不进明细**：用户加了行但没填完，库里不该留一条"无名食材"。
只填了名字没有克数的行也照收（明细里 `amount_gram` 为空），因为"有什么"比"多少"更基本。

## 五、约束 Ollama 输出格式：三道防线

**只靠系统提示词是不够的** —— 小模型（5.1B）在长输出时会漂移。所以要做三层：

| 防线 | 做法 | 作用 |
|---|---|---|
| **① 系统提示词** | 明确 JSON 结构 + 字段规则 + 示例（见 `prompts/dish-generate-system.txt`） | 告诉它要什么 |
| **② `format: "json"`** | Ollama 的约束解码参数 | **实测有效**：不加会裹 ` ```json ` 代码块，加了直接是纯 JSON |
| **③ 应用层校验 + 重试** | 反序列化后校验字段/类型/范围，不合格就带着错误重试一次 | 兜住剩下的小概率 |

第 ③ 层的重试策略建议：

```
第一次：正常提示词
   ↓ 校验失败
第二次：在原提示词后追加「上次输出有以下问题：xxx，请修正后重新输出」
   ↓ 仍失败
标记任务 FAILED，前端提示「生成失败，请重试」（不要无限重试 —— 那是烧资源）
```

**重试最多 1 次**，因为每次都要 3~10 秒，用户等不起。宁可失败让他重试。

### 5.4 实测结果与两个发现（提示词已据此改过一轮）

把 `dish-generate-system.txt` 原样发给 `gemma4:e2b`，跑 3 组食材、**13 条断言/组**，
结果 **39 PASS / 0 FAIL**。耗时 8~11 秒（输出 430~680 字符的 JSON）。

实测输出示例（用例 3）：

```
菜名    : 香菇豆腐青菜清炒
耗时/难度: 20 / 1
步骤    : 5 条，每条 25~29 字，都写了火候
食材    : 豆腐 200g / 青菜 250g / 香菇 100g
大厨建议: 2 条，每条 27~35 字
```

**发现 1：用量的幻觉会直接污染营养数据（已修）**

第一轮实测里，AI 对「土豆 + 牛肉」给出了：

```
料酒 300g   ← 实际炒菜也就 10~20g
```

因为营养 = `食材主数据 × 用量`，**300g 料酒会让热量和钠严重失真**。
已在提示词里补了用量范围（食盐 2~5g、酱油 10~20g、料酒 10~20g、油 10~30g…），
第二轮 `料酒 300g` 消失。

> 但这说明一件事：**AI 给的用量不能无条件信任**，应用层必须做钳制（见下）。

**发现 2：加了限制之后，AI 干脆不列调料了（**待你定策略**）**

第二轮三个用例的 `ingredients` 全部只剩主料和辅料，**盐、油、酱油全没了**。
这是典型的"小模型过度遵守规则"。

它带来一个真实后果：**炒菜的油热量被漏掉了**。
一道炒菜用 15g 油约 135 千卡 —— 漏掉之后，同一道菜的"热量"可能从 300 千卡掉到 165 千卡，
**差近一倍**，这对"营养参数"这个卖点是致命的。

三个可选方案：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `ingredients` 只放主料/辅料（参与营养计算）；另设 `seasonings` 字段放调料（位置给 AI，**用量由系统按菜式标准值取**，不采信 AI） | 职责清晰：AI 给"有什么"，系统给"多少"。油量可控 |
| B | 调料留在 `ingredients`，应用层按品类钳制用量 | 改动小，但"钳制阈值"要维护一张表 |
| C | 完全不管调料，只算主料营养 | 最省事，但**热量口径失真**，不推荐 |

无论选哪个，`营养参数` 的展示都要带上 `nutrition_verified` 标记（见 3.2）。

**发现 3：单次生成 8~11 秒**

比简单问答（3~4 秒）慢一倍多 —— 因为要输出 400~700 字符的结构化 JSON。
**这彻底坐实了"必须异步 + 队列"**：用户不可能对着转圈等 11 秒。

### 5.5 第四道防线：业务约束校验（改进阶段新增）

上面三道防线只管"JSON 长得对不对"，**管不了"模型有没有听用户的话"** ——
用户说不要花生、必须用牛肉、最多 30 分钟、只有炒锅，模型完全可以给你一份格式完美但全违反的菜谱。
所以改进阶段加了独立的约束校验层：

| 校验 | 做法 |
|---|---|
| 必用 / 禁用食材 | 按**归一化后的食材 ID** 比对（不是字符串包含 —— 「鸡蛋面」不能被当成「鸡蛋」） |
| 用量合理性 | 按「食材类别 × 人数」算克重上限，不是一个固定阈值套所有场景 |
| 最长耗时 / 可用设备 | 与请求里的约束逐项比对 |
| 步骤一致性 | 步骤里出现的食材必须能在配料表里找到（词典取自主数据，`MIN_NAME_LEN_FOR_STEP_SCAN = 2`）；反之必用食材必须在步骤里有用途 |

两个关键设计：

1. **格式合格与约束合格分开记录**（`DishDraftValidator.validateDetailed()` 返回
   `ValidationResult(problems, constraintProblems)`，`formatOk()` / `constraintOk()` 各算各的）。
   理由：格式不合格是"模型没按格式说"，约束不合格是"模型没听用户的话"，改进方向完全不同，
   混成一个"失败率"就没法用。记录落在 `t_ai_generation_record` 的 `format_ok` / `constraint_ok`。
2. **提交阶段就自检矛盾的约束**（`rejectContradictoryConstraints`）：必用 ∩ 禁用、
   手边食材 ∩ 禁用 → 直接拒绝，不让用户白等 6 分钟再告诉他不存在这样的菜。

约束还必须进**请求签名**（单飞去重的 key）：否则"忌口不同"的两次提交会被合并成同一个任务，
第二次提交的用户拿到的是按别人约束生成的结果。

> 实测里踩到的两个真 bug（都写进了 `.workbuddy/memory/PITFALLS.md`）：
> ① record 上的 `isBlank()` 被 Jackson 当 getter，序列化多写一个 `"blank"` 字段、读回来直接抛
> `UnrecognizedPropertyException` —— 症状是"任务提交能存、一执行就失败"；
> ② PowerShell 的 `Set-Content -Encoding UTF8` 会写 BOM，`javac` 报 `非法字符 '\ufeff'`。
> 两者都不是业务逻辑问题，但都让"看起来该通过"的链路整条挂掉。

### 5.6 人工可操作性评价：不能让生成模型自己评自己

改进要求里明确写了「记录约束违反率、重试成功率和**人工可操作性评分**，人工评价不能只由生成模型自身完成」。
格式/约束通过率是机器能算的，但"这份菜谱人愿不愿意照着做"只能由人来判断。为此把**准备工作**做成了工具
`es/eval/human-eval-kit.py`（人本身仍然是外部输入，工具替代不了）：

| 子命令 | 做什么 | 为什么这样设计 |
|---|---|---|
| `build` | 从 `t_ai_generation_record`（`status=2` 成功且有 `dish_id`）关联菜品，出 `blind-sheet.md`（菜名/配料含用量/步骤/建议）+ `ratings-template.csv` + `answer-key.csv` | **盲评**：序号用固定种子打乱，"哪条是加了参考菜谱生成的"只写在**不给评价者看的** `answer-key.csv` 里 —— 知道答案的评分者会不自觉偏向它 |
| `score` | 读所有 `ratings-<名字>.csv`，按臂汇总均分 / 符合率 / 会做率，并算评价者之间的**线性加权 Cohen's kappa**（有序 1-5 分不能当无序类别算） | 至少 2 人独立评分；只有 1 人时报告直接写"算不出一致度，等于用主观分替代客观分"。kappa 低于 0.4 要先怀疑**评分标准没讲清**，而不是怪评价者 |

`score` 已用假评分表验证过（两臂均分、成对 kappa、样本 <5 时拒绝下结论都跑通）。
但**当前数据还不能出结论**，两个原因必须一起交代：

1. **样本太薄**：成功生成且菜品未删的只有 7 条（A 臂 4 / B 臂 3），两臂都不到 5，报告只会写"定性观察"。
2. **两臂各自困在一个提示词版本上**：A 臂全是 `prompt_version=076b89e0`（加了参考菜谱规则之后），
   B 臂全是 `1379896b`（之前）。也就是说两臂差的**既是策略也是提示词**，跨版本比较无效。
   有效对比必须在**同一个提示词版本**下把两臂补齐（临时把 `ai.generate.enhance-enabled` 关掉再生成一批 B 臂）。

最后一条口径：人工分**替代不了**客观指标（`results-generation.{md,json}` 里的格式/约束通过率、重试成功率），
两者只能互相印证 —— 客观全过而人工分很低，恰恰说明校验器漏了真正要管的东西。

## 六、决策结果

| # | 决策点 | **你的决定** | 落地影响 |
|---|---|---|---|
| 1 | 队列权限边界 | **只能管理自己的任务** | `move` / `cancel` 前必须校验 `task.userId == 当前用户`；改顺序只在自己任务所占的下标集合内做交换（见 2.9） |
| 2 | 调料怎么处理 | **方案 A** | 提示词新增 `seasonings` 字段（AI 只给"要哪几样"，不给用量），用量由系统按标准配方补。**已落地并实测：69 PASS / 0 FAIL** |
| 3 | 执行中取消要不要"真省资源" | **暂时不做** | 只做逻辑取消（`Future.cancel(true)`），不引入流式 + 断连。**改进阶段实测代价**：取消不释放模型槽位，后续任务实测 `queue_wait_ms = 240142`（见 2.4） |
| 4 | 自由食材的营养怎么展示 | ~~AI 计算 + 标注「仅供参考」~~ → **改进阶段翻案：本地按成分表算为主，AI 估算降级并标注来源** | 实测 AI 估算与本地计算平均偏差 **181.79%**；来源与核对状态分别入库（见 3.2） |
| 5 | 并发度默认值 | **1**（实测后确认） | 配置项 `ai.queue.concurrency`；实测提到 2 会因 Ollama 并行 1 + 8G 显存而互相拖慢（见 2.5） |
| 6 | 评论要不要支持回复/点赞 | 待定（建议第一版只做一级） | 决定表结构复杂度 |
| 7 | 前端轮询间隔 | 待定（建议 1.5 秒） | 服务端压力 vs 体验 |
| 8 | AI 菜品默认草稿还是公开 | 待定（建议草稿） | 决定「我的菜品」页的数据来源 |
| 9 | 应用层要不要钳制 AI 给的用量 | **已做** | 提示词给用量范围 + `DishDraftValidator` 按「类别 × 人数」算上限（见 5.5） |

> 第 4 项在改进阶段被实测数据推翻并翻案：**文档里保留原来的判断和翻案理由**，
> 比直接改成"正确答案"更能说明这个决策是怎么来的。
> 第 5、9 项由实测定稿，不再是"待定"。
